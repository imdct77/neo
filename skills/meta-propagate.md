# ⚠️ 이 파일은 Hermes 내장 스킬이 아닙니다. NEO가 조건에 따라 직접 읽어 따르는 Neo 참조 문서입니다.


# meta-propagate — 메타 인덱스 전파

메타 인덱스(`harness/state/meta/src/`)는 코드베이스의 의미를 계층적으로 비추는 청사진이다.
이 스킬은 **변화가 생겼을 때 그 변화를 메타 인덱스에 반영하고 상위로 전파하는 방법**을 담는다.

전파는 드물게 일어난다 — 구조(디렉토리·파일)나 의미('디렉토리 목적'·'주요 함수')가
바뀔 때만이다. **TDD 반복(같은 파일 안에서 함수 본문을 고치는 루프)마다 돌리지 않는다.**
함수 시그니처·역할이 그대로면 전파할 것이 없다.

---

## 1. 역할 분리 — 구조는 코드, 의미는 LLM

```
python3 harness/hooks/meta_consistency_check.py --sync   →  구조(결정론)
    · 디렉토리의 직속 파일 목록을 정확히 유지(추가/삭제 반영)
    · 직속 하위 디렉토리 목록을 정확히 유지
    · 파일별 L3 skeleton(DETAIL.{stem}.md)을 scope 템플릿에서 생성
    · 새 항목엔 [AUTO] TODO placeholder를 넣고, 기존에 채운 의미는 보존

NEO(LLM)                                                 →  의미(판단)
    · placeholder([AUTO] TODO)를 실제 의미로 채운다
    · '디렉토리 목적'·'정체성'·'주요 함수 투영'을 작성한다
    · 변화가 상위 목적에 영향을 주는지 판정하고 전파한다
```

**먼저 `--sync`를 실행한다.** 코드가 구조를 맞춘 뒤, 남은 `[AUTO] TODO`를 LLM이 채운다.
`--sync`는 LLM이 채운 내용을 덮어쓰지 않는다(파일 경로를 키로 보존). 안심하고 돌려도 된다.

---

## 2. 해상도 사다리 — 같은 대상, 깊이만 다르게

L1·L2·L3는 같은 '주요 함수'를 점점 깊은 해상도로 비춘다. **진실의 원천(SoT)은 항상 L3.**
L1·L2는 L3 `주요 여부=주요` 함수의 투영일 뿐이다.

| 계층 | 파일 | 성격 | 주요 함수 해상도 |
|------|------|------|-----------------|
| L1 | `INDEX.md` | 청사진 | 한 줄 — `name: 요약` (파일 목록 괄호 안) |
| L2 | `DETAIL.md` | 구성 | 계약 — BE: `name(params)→return`+하는 일 / FE: 인터페이스+동작 계약 |
| L3 | `DETAIL.{stem}.md` | 디테일 | 전체 — 호출처·실패·중복 금지·수정 시 영향·의존성 |

'주요 여부'는 L3 생성 시점에 판정해 기록한다(BE: API 엔드포인트·외부 export·이벤트 /
FE: export·props-callback·서버 API·라우트의 네 경계). 한 번 판정하면 L1·L2는 그것을 읽기만 한다.

---

## 3. 채우기 규칙 (placeholder → 의미)

`--sync` 후 `[AUTO] TODO`가 남은 자리를 채운다.

- **L3 `DETAIL.{stem}.md`** (가장 먼저): 각 함수의 `주요 여부`를 판정 기준에 따라 정하고,
  `하는 일`·`외부 인터페이스/노출 경계` 등을 채운다. 이게 SoT이므로 먼저 채운다.
- **L1 `INDEX.md` 파일 목록**: `- \`path\` — {정체성} ({주요1}: {요약}, ...)`.
  괄호 안은 그 파일 L3의 `주요 여부=주요` 함수만, `하는 일`을 짧게 투영한다. 내부 헬퍼는 넣지 않는다.
- **L1 `INDEX.md` 디렉토리 목적**: 존재 이유·책임·경계를 충분히. 길이 제약 없음
  (전파 시 의미 비교의 기준이 되므로 빈약하면 안 된다).
- **L2 `DETAIL.md`**: 각 파일이 *왜 존재하는가* + 주요 함수의 *계약 요약*(해상도 표 참조).
- **L1 `INDEX.md` 공용 요소**: L3 `공용 여부`(전체 공용/도메인 공용/전용)의 투영.
  같은 기능 재구현을 막아 재사용을 높이기 위함. 전용은 넣지 않는다. 등급별 도달은 §4-5 참조.

---

## 4. 전파 알고리즘 — 자신이 속한 디렉토리에서 상위로

변화가 일어난 디렉토리를 D라 하자(예: `src/be/user/profile`).
D의 메타를 채운 뒤, **D의 부모로 올라가며** 아래를 반복한다.

### 4-1. 한 계층 전파 (부모의 L2 → L1 순서로 각각)

부모 디렉토리 P에서, 먼저 **L2(`P/DETAIL.md`)의 '하위 디렉토리'**, 그다음 **L1(`P/INDEX.md`)의
'하위 디렉토리'**에 대해 똑같이:

```
(1) 존재 체크 — grep으로 결정론적 확인
    grep -q "`D_name/`" P/DETAIL.md   (그리고 P/INDEX.md)
    · 없으면  → '하위 디렉토리' 표에 D를 등록('목적'은 D의 디렉토리 목적 요약 + 링크)
    · 있으면  → (2)로

(2) 목적 의미 비교 — LLM 판정
    표에 적힌 D의 '목적'이 D의 현재 '디렉토리 목적'과 의미적으로 같은가?
    · 같으면  → 수정하지 않음. 이 줄기는 여기서 멈춘다.
    · 다르면  → 표의 '목적'을 갱신하고 (3)으로
```

### 4-2. 전파 승급 — 목적 변화가 위로 타고 오르는 조건

```
(3) 부모 자신의 '디렉토리 목적'에 영향을 주는가? — LLM 판정
    방금 D의 목적이 바뀐 것이, P의 '디렉토리 목적'(P가 무엇인가)에 영향을 주는가?
    · 영향 없음 → P의 '디렉토리 목적'은 그대로. 전파는 여기서 멈춘다(중간에 끊김).
    · 영향 있음 → P의 '디렉토리 목적'을 갱신한다.
                  이 갱신이 새로운 트리거가 되어, P를 D로 삼아 4-1을 P의 부모에서 반복한다.
```

전파는 "하위 디렉토리 목록 갱신"에서 멈추지 않고, **"디렉토리 목적의 변화"로 승급될 때만**
위로 오른다. 대부분의 변화는 중간에서 끊긴다 — 그게 정상이다.

### 4-3. 최상위 도달

'디렉토리 목적' 변화가 scope 꼭대기(`be/` 또는 `fe/`)까지 닿으면,
최상위 `src/INDEX.md`에 반영해야 한다. 이건 `--sync`가 디렉토리 목록은 유지하지만,
바뀐 '목적'은 LLM이 최상위 표에 갱신한다.

### 4-4. 주요 함수 변경의 별도 경로

함수의 `주요 여부`나 `하는 일`이 바뀌면(시그니처·역할 변화), L3가 SoT이므로:
```
L3 갱신 → L2 계약 요약 갱신 → L1 파일 목록 괄호(한 줄 투영) 갱신
```
이 셋은 같은 파일을 다른 해상도로 비추므로 함께 맞춘다. 디렉토리 목적까지 바뀌면 4-1로 이어진다.

### 4-5. 공용 자산의 등급별 투영 (재구현 방지)

함수·컴포넌트의 L3 `공용 여부`가 바뀌면(전용→공용 승격 등), L1 '공용 요소'에 투영한다.
**등급이 투영 도달 높이를 정한다** — 재사용 신호가 닿아야 할 범위만큼만 끌어올린다:

```
도메인 공용  → 그 도메인 디렉토리의 INDEX.md '도메인 공용'까지만.
               (그 도메인 작업자만 알면 됨)
전체 공용    → 거기 더해 scope 루트(be/INDEX.md 또는 fe/INDEX.md)의 '전체 공용'까지.
               (도메인을 넘어 누구나 발견해야 재구현을 막음)
전용        → 공용 요소에 올리지 않는다.
```

전체 공용을 최상위 `src/INDEX.md`까지 올리지는 않는다(be/fe를 가로지르는 공용 자산은
사실상 없다 — 없는 경로를 위한 복잡성은 만들지 않는다). SoT는 L3 `공용 여부`,
L1 공용 요소는 그 투영일 뿐이다. reuse-check(`meta_search`)가 재사용 후보를 찾을 때
이 공용 자산이 1순위 표적이 된다.

## 5. ⛔ 공용 함수 수정·삭제 — 반드시 따르는 절차 (선택 아님)

**공용 요소(전체 공용·도메인 공용)에 생긴 작은 실수 하나가 그것을 쓰는 모든 곳을
동시에 깨뜨려 전체 코드베이스를 쓰레기로 만든다.** 그래서 공용 함수의 수정·삭제는
"해도 좋고 안 해도 좋은" 검토가 아니다. 아래 절차를 **반드시** 거친다.
자율성은 "여파를 어떻게 처리할지"에 있고, "절차를 거치느냐"에는 없다.

전용(`공용 여부=전용`) 함수는 대상이 아니다 — 한 곳에서만 쓰이므로 바로 고친다.
그러나 공용으로 등재된 함수는 예외 없이 아래를 따른다.

### 수정·삭제 전 (반드시)
```
1. 그 함수 L3(DETAIL.{stem}.md)의 역방향 의존성(BE: `Imported by` / FE: `사용처 used by`)을 읽어 사용처 전부를 확인한다.
2. Imported by가 비어 있으면 신뢰하지 말 것 — grep으로 역추적해 실제 사용처를 모두 찾아
   먼저 그 역방향 의존성 목록을 채운다. (비어 있음 ≠ 사용처 없음. 기록 누락일 수 있다.)
3. 이제 영향 범위가 손에 있다. 여기서부터 어떻게 대응할지는 판단(자율)한다.
```

### 시그니처·동작을 바꿀 때 (반드시)
```
· 사용처 전부를 같은 변경 안에서 함께 갱신한다. 하나라도 빠뜨리면 그곳이 깨진다.
· 갱신 후 영향받은 사용처의 테스트를 재실행해 회귀가 없음을 확인한다.
· L3의 '수정 시 영향'·시그니처를 갱신하고, §4-4 경로로 L2 계약·L1 투영까지 맞춘다.
```

### 삭제할 때 (반드시)
```
· 사용처가 하나라도 남아 있으면 삭제하지 않는다. 먼저 모든 사용처를 이전·제거한다.
· grep으로 사용처 0을 확인한 뒤에만 삭제한다.
· 삭제 후 L1 공용 요소·L2·L3에서 항목을 제거하고, 이 함수를 쓰던 파일들의 Import도 정리한다.
```

이 절차가 신뢰성 있게 작동하려면 **L3의 역방향 의존성(Imported by / 사용처)이 채워져 있어야 한다.**
공용 함수의 역방향 의존성을 비워두는 것은 다음 세션의 자신에게 지뢰를 남기는 것이다.
공용으로 판정한 함수·컴포넌트는 역방향 의존성을 반드시 채운다.

## 6. 정지 조건 (전파는 끊겨야 정상)

다음 중 하나면 그 줄기의 전파를 멈춘다:
- 부모 표의 '목적'이 현재와 의미적으로 같다 (4-1 (2))
- 목적이 바뀌었지만 부모의 '디렉토리 목적'에 영향이 없다 (4-2 (3))
- scope 최상위 `src/INDEX.md`에 도달해 반영을 마쳤다 (4-3)

끊기지 않고 끝까지 오르는 경우는 드물다. "모든 변화가 최상위까지 간다"면 의심하라 —
대개 '디렉토리 목적'을 너무 빈약하게 써서 영향 판정이 무뎌진 것이다.

## 7. 전파 완료 후 — 커밋 + HISTORY 기록 (시간선 보존)

메타 인덱스는 '공간에 대한 감각'이고, git 커밋과 HISTORY.md는 그것이 **어떻게 변해왔는가**를
시간선으로 조회하는 힌트다. 그래서 구조·의미 변화는 그 시점에 커밋으로 남겨야 한다.

### 언제 커밋하나
전파를 일으키는 **구조·의미 변화**가 끝났을 때다 — 생성·삭제·이동, 시그니처 변화,
`디렉토리 목적`·`주요 여부`·`공용 여부` 변화. **TDD 본문 수정(같은 함수를 반복 수정)처럼
전파가 없는 변화는 커밋하지 않는다.** 모든 키 입력을 남기면 시간선이 노이즈로 가려진다 —
남길 것은 '의미 있는 변화'다. (Phase 완료 커밋은 그대로 유지된다 — 그건 더 큰 이정표다.)

### 무엇을 커밋하나
project 소스와 harness 메타를 **각자의 레포에 커밋**한다(2-repo). pre-commit이 메타를
자동 sync·stage하므로, 메타 레포 커밋엔 갱신된 인덱스가 포함된다. 두 커밋은 HISTORY.md가
양쪽 해시를 함께 적어 연결한다.

### HISTORY.md 기록 (반드시)
커밋 후 `harness/state/meta/src/HISTORY.md`(활성 파일)에 시간순으로 한 항목을 append한다:
```
## {날짜} · {CREATE|MODIFY|DELETE|RENAME} · {대상 경로}
- 무엇: {무엇이 바뀌었나}
- 왜:   {왜 — 설계 의도·요구사항 변화}
- 전파: {어디까지 전파됐나}
- 커밋: project {hash} / harness {hash}
```
그리고 변화한 디렉토리의 L1 INDEX '최근 변경' 포인터를 그 날짜로 갱신한다.
기존 항목은 수정·삭제하지 않는다(이력 보존). 년 단위로 아카이브한다(연말에
`HISTORY-{연도}.md`로 분리, 활성 파일은 `HISTORY.md` 유지). 이 '왜'의 기록이 나중에
"무엇이 삭제됐나 → 그 시점 메타·소스는 어떻게 기술돼 있었나"를 거슬러 검토하는 출발점이 된다.

특히 §5(공용 함수 삭제)처럼 영향이 큰 변화일수록 HISTORY 기록이 중요하다 —
나중에 "이게 왜 사라졌지"를 추적할 유일한 단서이기 때문이다.

## 8. 실행 순서 요약

```
1. python3 harness/hooks/meta_consistency_check.py --sync   # 구조 동기화
2. 변화한 디렉토리 D의 L3 → L1 → L2 placeholder 채우기        # 의미 (SoT부터)
```

## 9. 왜 LLM이 하는가 (전파를 코드로 내리지 않는 이유)

존재 체크는 grep(결정론)이지만, **"목적이 의미적으로 같은가", "이 변화가 상위 목적에 영향을
주는가"는 의미 판정**이라 LLM만 할 수 있다. 그리고 이 판정 과정 자체가
"요구사항 변화에 어떻게 대응했는가"라는 학습 신호다 — 코드로 내리면 그 신호가 사라진다.
전파 빈도가 낮아(구조적 사건에서만 발생) LLM 주도의 비용은 작다.
훗날 전파가 병목으로 측정되면, 그때 존재 체크·구조 갱신만 코드로 내린다(현재는 `--sync`가 그 경계).
