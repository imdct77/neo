# phase0 — 사전 설계 검토

코드를 작성하기 전에 반드시 이 스킬을 실행한다.
"간단한 기능이라도" 예외 없다. 검토 없이 구현한 결과가 기술 부채다.

## Step 0. mem0 탐색 — 적합성·영향도 사전 평가

AC 검토 전에 과거 결정과 학습을 불러온다.
이 단계가 없으면 AC는 현재 컨텍스트만으로 판단한다.
mem0에 데이터가 쌓일수록 이 단계의 품질이 높아진다.

```
[적합성 평가] — 이 변경이 기존 설계 원칙과 맞는가

탐색 A: 과거 아키텍처 결정
  키워드: "AC: {요청과 관련된 키워드}"
  예) Fork 관련 요청 → "AC: Fork" "AC: recipe" "AC: 복사"
  목적: 이미 내려진 설계 결정과 충돌하는지 확인

탐색 B: 발견된 함정·패턴
  키워드: "LEARN: {관련 도메인}" "LEARN: {관련 기능}"
  목적: 같은 실수를 반복하지 않기 위한 맥락 확보

탐색 C: .hermes.md Omission Constraints 대조
  이미 컨텍스트에 있으므로 탐색 불필요
  요청 내용과 절대 금지선을 직접 대조
```

```
[영향도 평가] — 이 변경이 어디에 영향을 주는가

탐색 D: 완료된 태스크 목록
  키워드: "NEO: {관련 도메인} 완료" "NEO: {TASK_ID}"
  목적: 이미 구현된 코드 중 영향받는 것 파악

탐색 E: 기존 ADR
  키워드: "ADR" "AC: 결정"
  목적: 이전 아키텍처 결정과 연관된 변경인지 확인

탐색 F: BADCASE 학습
  키워드: "BADCASE: {현재 도메인}" "BADCASE: DESIGN"
  목적: 감리·내부검토에서 발견된 이 도메인의 실수 패턴 파악
  처리: 발견 시 AC 검토 시 특히 주의 깊게 다룸
```

탐색 결과 정리 후 사람에게 먼저 보고:
```
"mem0 탐색 결과:

 [적합성]
   관련 과거 결정: {ADR 또는 LEARN 기록 요약}
   충돌 가능성: {있음/없음/확인 필요}

 [영향도]
   영향받는 구현: {완료된 TASK_ID 목록 또는 없음}
   연관 도메인: {있음/없음}

 이 맥락을 바탕으로 AC 검토를 시작합니다."
```

mem0 기록이 없으면:
```
"관련 mem0 기록 없음. 첫 번째 검토입니다.
 AC 검토를 시작합니다."
```

## Step 0-1. 코드베이스 유사 기능 탐색 (구현 전 필수)

**새 기능 구현 전에 반드시 실행한다. 이미 있는 것을 다시 만들지 않기 위해.**

> **우선 도구: meta_search (의미 기반 — grep보다 먼저).**
> 메타 인덱스(state/meta)는 grep 대신 의미 기반으로 탐색하기 위해 존재한다.
> 만들려는 각 함수에 대해 reuse-check를 먼저 실행한다.
>
> ```
> # 1) 만들려는 함수마다 재사용 후보 확인 (DRY)
> python3 harness/hooks/meta_search.py reuse-check \
>     --name {만들려는_함수명} --desc "{한 줄 설명}"
>   → 동일/유사 후보가 나오면: 신규 작성 대신 재사용·확장을 우선 검토.
>   → 후보 없음: 신규 작성 진행.
>
> # 2) 기능 영역 전반의 관련 코드 탐색
> python3 harness/hooks/meta_search.py search "{기능 키워드}"
> ```
> 주의: meta_search는 L3 상세가 채워진 함수만 찾는다(skeleton 제외).
> 결과가 비면 아직 색인 안 된 것일 수 있으므로 아래 grep으로 보완한다.

```
탐색 대상 1 — 유사 함수·클래스·컴포넌트
  먼저: meta_search reuse-check / search (위)
  보완(메타 인덱스 미색인분): grep
    BE: grep -r "{기능 키워드}" src/be/
    FE: find src/fe/ -name "*.tsx" | xargs grep -l "{기능 키워드}"

  발견 시 판단:
    동일 기능  → 재사용. 구현 생략.
    유사 기능  → 확장·리팩토링 방향 검토 (Step 1에서 AC에게 보고)
    다른 기능  → 신규 구현 진행

탐색 대상 2 — 유사 상수·타입·인터페이스
  BE: grep -r "{상수명 후보}" src/be/core/ src/be/constants/
  FE: grep -r "{상수명 후보}" src/fe/constants/ src/fe/types/

  발견 시: 새로 정의하지 않고 import해서 사용

탐색 대상 3 — 과거 내력 (왜 이렇게 돼 있나)
  meta_search가 '무엇이 있나'를 찾는다면, HISTORY는 '왜·어떻게 이렇게 됐나'를 찾는다.
  작업 대상 디렉토리·기능이 과거에 어떻게 변해왔는지 본다 — 같은 실수를 반복하거나
  의도적으로 제거된 것을 되살리는 것을 막는다.
    1) 작업 대상 L1 INDEX의 '최근 변경' 포인터를 본다(있으면 그 날짜로 진입).
    2) grep으로 시간선에서 관련 항목을 좁힌다:
       grep -nE "{기능·경로 키워드}" harness/state/meta/src/HISTORY.md
       (과거 연도는 harness/state/meta/src/HISTORY-{연도}.md)
  발견 시: 그 변경의 '왜'를 읽어, 과거에 제거·변경된 의도를 존중한다(되살리기 전 재검토).

탐색 결과 보고 형식:
  "유사 기능 탐색 결과 (meta_search + grep):
   - {발견된 파일/함수명}: {유사도 — 동일·유사·무관} {meta_search 근거}
   - 재사용 가능 여부: {가능 / 확장 필요 / 신규 구현 필요}
   - 재사용 시 적용 패턴: {재사용·파라미터 추가·인터페이스 추출·별도 구현}"
```

**이 단계를 건너뛰고 구현한 코드는 review.md 검토에서 중복 구현으로 반려될 수 있다.**

## Step 0-2. 결정의 가역성 판별 — 일방통행문 점검 (다분기 탐색 트리거)

신규 구현이 확정되면, 그것이 *되돌리기 쉬운 결정*인지 *어려운 결정*인지 먼저 판별한다.
되돌리기 어려운 결정(일방통행문)에서 틀리면 배포 후 수정 비용이 설계 단계의 15~100배가 된다.
AI는 변수 이름 짓기와 DB 선택을 동등하게 취급하는 함정이 있다 — 가역성 필터를 의식적으로 적용한다.
(근거·데이터 구조: `docs/RESEARCH_multi-branch-exploration.md`, `docs/DATA_multi-branch-exploration.md`)

```
자문 점검 (하나라도 '예'면 일방통행문 후보):
  □ 데이터 모델·DB 스키마를 정의/변경하는가? (데이터 누적 후 마이그레이션 불가역)
  □ 핵심 도메인 모델(문제의 중심 엔티티)을 정의하는가?
  □ 서비스 경계·모듈 분할을 긋는가? (가로지르는 변경은 전면 재작업)
  □ 통신 패턴·데이터 흐름의 근간을 정하는가?
  □ 인증·권한 구조를 정하는가?
  □ 기술 스택·영속성 기술을 선택하는가?
  □ (구조 예측) 여러 곳이 의존할 공용 자산이 되는가? 외부 경계(API·라우트·export)를 새로 정하는가?

확정 테스트 (후보 → 진짜 일방통행문):
  "이 결정을 나중에 바꾸려면 비싼가?" — 데이터 누적·전면 재작업·외부 영향 중
  하나라도 크면 '예'. 작은 설정 테이블처럼 바꿔도 싸면 양방향문 → 그냥 진행(다분기 불필요).

양방향문 (되돌리기 쉬움 — 다분기 불필요, Step 0-3으로):
  UI 프레임워크·폴더 구조·명명 규칙·내부 컴포넌트 설계·도구/라이브러리 선택.
```

일방통행문 감지 시 (반드시 — 조용히 단일 구현하지 않는다):
  감지는 네오가, 발동은 사람이 한다. 사용자에게 위험을 인지시키고 선택을 맡긴다:
```
  "이건 되돌리기 어려운 결정으로 보입니다(이유: {어느 일방통행문}).
   세 가지 중 고르실 수 있습니다:
     1) 다분기 탐색 — 서로 다른 구현 3~5개를 만들어 평가·비교
     2) 디커플링 — 추상화로 결정을 가역으로 전환(일방통행문 → 양방향문)
     3) 결정 연기 — 더 많은 정보를 얻을 때까지 미룸
   어떻게 진행할까요?"
```
  → 1) 선택 시: exploration_record 생성(trigger.path=semantic 또는 structural,
    mode=proactive, one_way_door={유형}). 분기점 = 현재 커밋. (DATA 문서 스키마)
  → 사람의 지목(경로 3): 사용자가 먼저 "이건 신중히, 여러 안 보고 싶다"고 하면
    점검을 건너뛰고 바로 1)로 간다.
  → 과대 감지 방지: 확정 테스트를 통과 못 하면(되돌려도 싸면) 플래그하지 않는다.

### 셋 중 무엇을 권하나 (다분기 vs 디커플링 vs 연기)
같은 일방통행문이라도 상황에 따라 권할 선택지가 다르다. 판단 기준:
```
바뀔 가능성 높음(요구 유동적·기술 미성숙) → 디커플링. 어차피 바꿀 거면 싸게 바꾸게 만든다.
바뀔 가능성 낮으나 틀리면 치명적     → 다분기. 오래 갈 결정이니 신중히 잘 고른다.
지금 정보 부족                       → 연기. 더 알게 될 때까지 미룬다.
```
다분기와 디커플링은 불가역성에 대한 정반대 전략이다 — 다분기는 *결정의 품질*을 높이고,
디커플링은 *결정의 비용*을 낮춘다. 디커플링이 성공하면 다분기가 불필요해진다(나중에 싸게 바꿈).

### 디커플링 — "일방통행문을 양방향문으로" 구체 기법
불가역성은 대개 "결정이 코드 전체에 퍼져, 바꾸려면 퍼진 곳을 다 고쳐야 함"에서 온다.
디커플링은 그 퍼짐을 끊어 결정 변경을 *국소적*으로 만든다(= 양방향문화).
```
기법 1 — 인터페이스 뒤로 숨기기 (핵심)
  결정을 인터페이스 뒤에 가둔다. 코드는 인터페이스만 알고 구현(=결정)은 모르게.
  예: 코드가 recipeRepo.getAncestors(id)만 호출 — 인접리스트인지 클로저테이블인지 모름.
  나중에 스키마를 바꿔도 인터페이스 뒤만 고치면 됨. §5의 역방향 의존성 축소와 같은 원리.

기법 2 — 결정을 데이터/설정으로 빼기
  하드코딩된 결정은 코드를 고쳐야 바뀌지만, 설정·데이터로 빼면 코드를 안 건드리고 바꾼다.
  "이 결정이 코드 로직인가, 파라미터인가?" — 파라미터면 빼낸다.

기법 3 — 변환 계층 두기 (데이터 불가역성 완화)
  데이터가 쌓이는 불가역성은 인터페이스만으론 부족(이미 쌓인 데이터가 옛 스키마에 묶임).
  스키마 버전 필드 + 읽을 때 옛 버전을 새 형식으로 변환하는 계층을 처음부터 둔다.
  "데이터가 쌓여 못 바꾼다" → "변환 계층을 추가하면 바꾼다".
```
**디커플링도 공짜가 아니다** — 인터페이스·변환 계층은 추상화 비용이며 Anti-Gold-Plating과
충돌한다. 모든 결정을 디커플링하면 추상화 지옥이 된다. **일방통행문 중에서도 "정말 바뀔
가능성이 있는" 것에만** 선별 적용한다.

## Step 0-3. 증분 구현 전략 선택

양방향문이거나(Step 0-2), 다분기 탐색이 한 후보로 정해진 뒤, 수직 슬라이싱으로 태스크를 분해한다.

**전략 선택 기준**:
- 기본: 수직 슬라이싱 (Vertical Slices) — 한 기능의 전체 스택을 먼저 완성
- BE·FE 분리 작업: 계약 우선 (Contract-First) — API 계약 정의 후 병렬 구현
- 불확실성 높은 기능: 리스크 우선 (Risk-First) — 가장 위험한 부분 먼저 증명

상세 규칙은 `harness/skills/templates/shared/incremental-impl.md` 참조.

**핵심 원칙**:
> "비슷한 코드 세 줄이 성급한 추상화보다 낫다. (Three similar lines > premature abstraction)"
> "가장 단순하게 동작하는 것은 무엇인가? (What is the simplest thing that could work?)"

## Step 1. AC 기본 검토

Step 0의 탐색 결과를 컨텍스트로 갖고 AC 관점에서 검토한다.
과거 결정과 충돌이 감지됐으면 그 지점을 먼저 짚는다.

```
검토 항목:
  □ 이 기능이 AGENTS.md의 MVP 범위 안인가?
  □ 기존 아키텍처(project/docs/design/architecture.md 또는 project/docs/specs/)와 충돌하는가?
  □ Step 0에서 발견된 충돌 가능성 재확인
  □ Q1~Q7 게이트 중 해당하는 것이 있는가?
     Q1: 외부 시스템 추가?
     Q2: DB 스키마 변경?
     Q3: 기존 API 변경?
     Q4: 여러 도메인 영향?
     Q5: 비가역적 작업?
     Q6: 성능·비용·보안 영향?
  □ 사람이 미처 생각하지 못한 엣지 케이스는?

질문 방식 (소크라테스식 — 한 번에 하나씩):
  1. "이 기능이 없으면 사용자가 어떤 불편을 겪는가?"
  2. "언제 이 기능이 완성됐다고 볼 수 있는가?"
  3. "이 기능이 실패하는 상황은 무엇인가?"
  4. "이 기능이 건드리지 않아야 하는 것은?"
  5. "기존 설계와 충돌하는 지점이 있는가?"

질문 방식 (보안·엣지 케이스 강화 — Secure Vibe Plan Mode):
  위 5개 질문 외에, 기능의 복잡도에 따라 추가 3~5개 질문:
  6. "이 기능에서 가장 위험한 보안 경계는 어디인가? (입력 검증·인증·권한)"
  7. "이 기능이 예상보다 100배 많은 데이터를 처리해야 한다면 어디가 무너지는가?"
  8. "이 기능이 의존하는 외부 서비스가 다운되면 사용자는 무엇을 보게 되는가?"
  9. "이 기능이 잘못 구현되면 어떤 데이터가 손상될 수 있는가?"
  10. "이 기능에 새 의존성이 필요한가? 있다면 실제로 존재하는 패키지인가?"
  → 계획 모드에서 이 질문들을 건너뛰지 않는다. AI의 정확도가 80%일 때,
    20개 결정 중 하나라도 틀리면 종단 정확도는 1.15%로 떨어진다.
```

Step 0에서 충돌이 발견된 경우 AC가 먼저 명시:
```
"과거 결정({ADR 또는 LEARN 요약})과 충돌합니다.
 이 변경을 진행하려면 해당 결정을 먼저 재검토해야 합니다."
```

검토 완료 후:
```
"이 시나리오에 대한 기본 검토가 완료됐습니다.
 BE·FE 의견을 추가하여 통합 의견을 들어보시겠습니까?"
```

## Step 2. BE·FE 확장 검토 (사람이 "예"일 때만)

BE·FE는 독립적 관점이므로 병렬로 실행한다:

```python
delegate_task(tasks=[
    {
        "goal": "BE 관점 시나리오 검토",
        "context": "{시나리오 전문}\n검토 관점: API구조·트랜잭션·엣지케이스·기존구현충돌\n결과 형식: DONE + 의견 요약",
        "toolsets": ["file"]
    },
    {
        "goal": "FE 관점 시나리오 검토",
        "context": "{시나리오 전문}\n검토 관점: STATE분기·EVT·UX케이스\n결과 형식: DONE + 의견 요약",
        "toolsets": ["file"]
    },
])
```

→ BE·FE 결과 동시 수집

AC가 BE·FE 의견 취합 → 종합 의견 제시

## Step 3. 설계 문서 저장 + Self-review

```
저장: project/docs/specs/YYYY-MM-DD-{topic}-design.md
(Step 0 탐색 결과 — 관련 과거 결정·충돌 여부 — 를 문서에 포함)

Self-review 체크:
  □ "TBD", "TODO", "미정" → 발견 시 즉시 수정
  □ 앞뒤 모순 → 수정
  □ "빠르게", "적절히" 같은 모호한 표현 → 구체화
  □ MVP 범위 초과 내용 → 별도 섹션으로 분리
  □ Step 0에서 발견된 충돌이 문서에 명시됐는가?

통과 후: "project/docs/specs/{파일명} 저장했습니다. 검토해주세요."
```
