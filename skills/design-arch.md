# design-arch — architecture.md 작성 기준

담당: AC 주도

---

## 작성 절차

```
Step 0. `skills/templates/README.md` 확인 → 적용 가능한 패턴이 있으면 `_design.md` 로드
Step 1. AC! → architecture.md 초안 작성
Step 2. NEO! → 사람에게 검토 요청
Step 3. 사람 피드백 반영 → 확정
Step 4. mem0 저장: "AC: architecture.md 확정, 날짜: {YYYY-MM-DD}"
```

---

## 파일 위치

```
project/docs/design/architecture.md
```

---

## 포함 내용

```
## 시스템 구성 개요
  - 전체 컴포넌트 구성 (텍스트 다이어그램)
    예)
      [클라이언트] → [API 서버] → [DB]
                              → [캐시]
                              → [외부 서비스]
  - 컴포넌트 간 데이터 흐름

## 기술 스택 상세
  - 각 레이어별 선택 이유
  - 버전 및 주요 라이브러리
  (AGENTS.md 섹션 2와 동기화 유지)

## 운영 고려사항
  - 예상 트래픽 규모 (초기 / 성장 시)
  - 스케일링 전략 (수직 / 수평)
  - 장애 대응 방침 (폴백, 재시도 등)

## 보안 원칙
  - 인증·인가 방식
  - 데이터 보호 정책
  - 핵심 보안 제약 (.hermes.md Omission Constraints와 연동)

## 핵심 설계 결정사항
  형식:
    결정: {무엇을 결정했는가}
    이유: {왜 이 선택인가}
    대안: {고려했지만 선택하지 않은 것과 이유}

## 변경 이력
  | 날짜 | 변경 내용 | 이유 |
  |------|----------|------|
```

---

## 갱신 시점 및 정책

```
갱신 트리거:
  - Q1(외부 시스템·라이브러리 추가) 게이트 통과 후
  - 스택 변경 승인 후

갱신 절차:
  AC! → 변경 내용 반영 → 변경 이력 섹션에 추가
  → mem0 저장: "AC: architecture.md 갱신, {변경 내용 한 줄}, {날짜}"

절대 금지:
  - 변경 이력 삭제 금지
  - AGENTS.md 섹션 2와 불일치 상태로 방치 금지
    (스택이 바뀌면 두 파일을 함께 갱신)
```

## Self-review 체크리스트

작성·갱신 후 반드시 확인:
```
□ "TBD", "추후 결정" 표현 없음
□ AGENTS.md 섹션 2 기술 스택과 일치

□ 운영 고려사항에 구체적 수치 있음 (예: "트래픽 많을 때" → "MAU 1만 기준")
□ 변경 이력 최신화
```
