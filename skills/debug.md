# debug — 체계적 디버깅

버그가 발생하면 즉시 코드를 수정하지 않는다.
증상 수정은 실패다. 근본 원인을 찾는 것이 디버깅이다.
Phase 1을 완료하기 전에는 수정안을 제시하지 않는다.

## Phase 1 — 재현 (Reproduce)

```
목표: 버그를 일관되게 재현하는 최소 케이스 만들기

실행:
  pytest {관련 테스트} -v
  또는 최소 재현 스크립트 작성

재현이 안 되면:
  "재현이 되지 않습니다. 어떤 조건에서 발생하는지 더 알려주세요."
  → Phase 2로 넘어가지 않는다

재현 성공 후:
  "재현 케이스: {최소 재현 조건}"
```

## Phase 2 — 가설 수립 (Hypothesize)

```
콜 스택 역방향 추적:
  증상 발생 지점
  → 호출한 함수
  → 그 함수를 호출한 함수
  → 원래 트리거

가설: "왜 이 버그가 발생하는가?"
  근거 없이 코드를 수정하지 않는다.
  추측으로 여러 곳을 동시에 변경하지 않는다.

변경 시점 추적 (HISTORY):
  "언제부터 이랬나"가 가설을 좁힌다. 최근 동작하던 것이 깨졌다면 그 사이의
  구조·의미 변화가 유력하다. 시간선에서 관련 변경을 찾는다:
    grep -nE "{증상 관련 경로·기능}" harness/state/meta/src/HISTORY.md
    (과거 연도는 HISTORY-{연도}.md)
  발견 시: 그 변경의 '왜'와 '무엇'을 읽고, 그 커밋 해시로 당시 상태를 확인한다
    (git show {hash} / git checkout {hash} -- {경로}).
  '무엇이 사라졌나'가 의심되면 HISTORY의 DELETE 항목을 먼저 본다 —
  삭제는 코드에 흔적이 없어 HISTORY가 유일한 단서다.
```

## Phase 3 — 검증 (Validate)

```
가설이 맞는지 확인하는 방법 실행:
  로그 추가, 중간 변수 출력, 테스트 케이스 추가

검증 없이 Phase 4로 넘어가지 않는다.
```

## Phase 4 — 수정 (Fix)

```
근본 원인이 확인된 후에만 수정한다.
수정 후 재현 케이스로 반드시 재테스트한다.
원래 실패하던 테스트가 통과하는지 확인한다.
```

## 3번 수정이 실패하면 멈춘다

```
"3번 수정이 실패했습니다.
 아키텍처 문제일 가능성이 높습니다.
 설계를 재검토할까요?"
→ phase0 스킬로 전환
```

## 완료 후

```
mem0 저장 (LEARN — 예측 포함 형식):
  "LEARN: [관찰] {발생한 패턴}
          [원인] {근본 원인}
          [수정] {어떻게 고쳤는가}
          [예측] {다음에 같은 상황에서 이 수정이 효과적일 것이다}
          [검증] {다음 유사 태스크에서 확인}"

이 debug 세션에서 스킬 흐름 자체에 문제가 있었는가?
  (예: 재현 단계가 불필요하게 복잡했다, 가설 단계가 빠졌다 등)
  → 있으면: mem0 저장: "SKILL_ISSUE: debug — {문제} — {개선 제안}"
  → 없으면: 넘어간다

스킬 파일 언로드.
```
