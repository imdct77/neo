# HISTORY — src 트리(소스 코드 + 메타 인덱스) 변경 시간선

이 파일은 `src/` 트리(소스 코드와 그 메타 인덱스)에서 **무엇이 언제 왜 바뀌었는가**의
의미 로그다. (코드와 무관한 다른 상태 메타의 이력은 여기 두지 않는다 — 범위는 src 트리.) git 커밋(스냅샷)과 짝을 이뤄,
"그 시점의 메타·소스가 어떻게 기술돼 있었나"를 거슬러 검토하는 출발점이 된다.

## 언제 읽나 (읽기 국면)
- **새 작업 전**(phase0 Step 0-1 탐색 대상 3): 작업 대상이 과거에 왜·어떻게 변해왔나 —
  의도적으로 제거된 것을 되살리지 않기 위해.
- **디버깅 중**(debug Phase 2): '언제부터 이랬나'로 가설을 좁힌다. 특히 'DELETE' 항목은
  코드에 흔적이 없는 삭제의 유일한 단서다.
- 각 L1 INDEX의 '최근 변경' 포인터가 이 시간선의 진입점이다.

## 기록 규칙
- **언제 기록하나**: 구조·의미 변화(생성·삭제·이동, 시그니처·`디렉토리 목적`·`주요 여부`·
  `공용 여부` 변화)와 그 전파가 끝났을 때. TDD 본문 수정처럼 전파가 없는 변화는 기록하지 않는다.
- **append-only, 시간순(오래된 것이 위)**. 기존 항목은 수정·삭제하지 않는다(이력 보존).
- **양 레포 커밋 해시를 함께** 적는다(project 소스 + harness 메타). 이게 의미↔스냅샷의 다리다.
- **년 단위 아카이브**: 활성 파일은 항상 `HISTORY.md`. 연말(첫 항목이 새해로 넘어가는 시점)에
  직전 연도분을 `HISTORY-{연도}.md`로 잘라 보관하고 활성 `HISTORY.md`는 비운다.
  새 항목은 언제나 `HISTORY.md`에 append하므로 기록 경로가 단순하다.
- 자세한 절차는 `harness/skills/meta-propagate.md §7`을 따른다.

## 항목 형식
```
## {YYYY-MM-DD} · {CREATE|MODIFY|DELETE|RENAME} · {대상 경로}
- 무엇: {무엇이 바뀌었나 — 한두 줄}
- 왜: {왜 바뀌었나 — 설계 의도·요구사항 변화}
- 전파: {어디까지 전파됐나 — 상위 디렉토리 목적 갱신 여부 등}
- 커밋: project {hash} / harness {hash}
```
