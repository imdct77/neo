## 1. 현행 접근의 구조적 문제

### 1.1 grep — 구문 검색이지 의미 검색이 아니다

```
grep -r "{기능 키워드}" src/be/
```

이 방식의 근본 결함:

| 문제 | 설명 |
|------|------|
| **키워드 의존** | `grep "payment"`는 `billing.py`를 놓친다. `grep "price"`는 `fee_calculator.py`를 놓친다. 같은 기능을 다른 이름으로 구현했으면 검출 불가. |
| **맥락 무지** | 검색 결과는 텍스트 매칭일 뿐이다. 그 함수가 정말로 "내가 찾는 기능"인지 구별하려면 파일을 직접 읽어야 함 → grep이 오히려 일을 늘린다. |
| **LLM 비효율** | BE가 수백 줄의 grep 결과를 읽고 판단해야 한다. 구현보다 탐색에 더 많은 토큰을 쓴다. |
| **언어 종속** | `grep -r`은 Python/Node/Go에서 동작하지만, 함수 시그니처 패턴은 언어마다 다르다. `def`, `func`, `const`, `export function` — grep은 구문을 알지 못한다. |
| **컨테이너 제약** | `grep`이 Docker 컨테이너에서 항상 사용 가능하다는 보장이 없다. search_files 도구가 있지만 이 역시 텍스트 매칭일 뿐. |

### 1.2 find + xargs — 프레임워크 종속

```bash
find src/fe/ -name "*.tsx" | xargs grep -l "{키워드}"
```

- `*.tsx`는 React/TypeScript 전용. Vue는 `.vue`, Svelte는 `.svelte`, Angular는 `.ts` + `.html`. 범용성 위배.
- Shell pipe(`|`)는 컨테이너 환경에서 불안정할 수 있다.

### 1.3 `constants/`, `types/` 경로 — 범용성 위배

```bash
grep -r "{상수명 후보}" src/be/ constants/
grep -r "{상수명 후보}" src/fe/constants/ src/fe/types/
```

방금 합의한 **"`src/be/`, `src/fe/`까지만 Neo가 정하고 하위 구조는 프로젝트 자유"** 원칙과 정면 충돌. NestJS는 `constants/` 없이 모듈별로 상수를 분산하고, Go는 `types/` 대신 패키지 단위로 타입을 정의한다.

### 1.4 DRY 원칙 자체의 구현이 DRY하지 않다

BE와 FE가 **똑같은 구조의 탐색 로직을 각자 중복해서 들고 있다**. 둘 다 "비슷한 것 찾기 → 재사용 판단 → 상수 충돌 확인"이라는 동일한 패턴인데, BE는 BE식으로, FE는 FE식으로 중복 기술돼 있다. DRY의 아이러니다.

## 2. CEO 제안: `docs/meta/src/` 구현 명세 메타 파일

### 2.1 제안 평가

| 장점 | 설명 |
|------|------|
| **의미 기반 탐색** | grep은 "어디에 `price`라는 문자열이 있는가"를 찾지만, meta는 "가격 계산을 담당하는 모듈은 어디인가"를 알려준다. 근본적 해결. |
| **LLM 친화적** | 마크다운은 LLM이 읽고 이해하기에 최적. grep 결과 200줄보다 meta 인덱스 50줄이 더 적은 토큰으로 더 정확한 판단을 내린다. |
| **언어·프레임워크 독립** | `.md` 파일은 모든 언어에서 동일하게 동작. `*.tsx` 같은 확장자 의존성 제거. |
| **Neo 산출물과의 통합** | `docs/` 아래 배치되어 기존 docs 디렉토리 정책과 일관성 유지. |
| **점진적 구축** | 코드를 쓸 때마다 meta도 같이 쌓인다. "한 번에 만들기" 부담 없음. |

### 2.2 보완이 필요한 지점

1. **작성 주체가 모호하다** — 누가 meta를 쓰는가? BE/FE가 직접? NEO가 취합?
2. **동기화 보장** — 코드는 수정됐는데 meta는 갱신 안 되면 오히려 grep보다 못한 misinformation이 된다.
3. **중복 기술** — meta의 설명과 코드 내 docstring/주석이 중복될 위험.
4. **디렉토리 구조 강제** — meta 트리가 `src/`의 디렉토리 트리를 그대로 따라가면, 프로젝트 구조 변경 시 meta도 전면 재작성.

## 3. 개량 제안: NEO 주도 메타 인덱스 + Task Brief 연동

### 3.1 핵심 아이디어

**meta는 NEO(orchestrator)가 관리한다.** BE/FE는 구현 시 "구현 명세 요약"을 Task Brief 완료 보고에 포함하고, NEO가 이를 meta 인덱스에 통합한다.

```
Task Brief → BE/FE 구현 → 완료 보고(구현 요약 포함) → NEO가 meta 갱신
```

### 3.2 디렉토리 구조

```
docs/meta/
  src/
    INDEX.md           ← 전체 코드베이스 개요 (BE+FE 통합 진입점)
    be/
      INDEX.md         ← 백엔드 디렉토리 트리 인덱스
      {domain}/
        INDEX.md       ← 도메인별 모듈 인덱스 (파일 목록 + 용도)
    fe/
      INDEX.md         ← 프론트엔드 디렉토리 트리 인덱스
      {domain}/
        INDEX.md       ← 도메인별 컴포넌트 인덱스
```

`INDEX.md` 체계는 CEO 제안의 계층 구조를 단순화한 형태: 디렉토리별로 하나의 인덱스 파일만 유지(파일별 개별 meta X). 이유는 유지보수 부담을 줄이기 위함. 파일이 너무 많은 프로젝트는 디렉토리 수준 인덱스로 충분.

### 3.3 BE용 INDEX.md 형식

```markdown
# src/be/auth/ — 인증 도메인

## 디렉토리 목적
사용자 인증·권한 관리를 담당. JWT 발급·검증, OAuth 연동, 세션 관리 포함.

## 파일 인덱스

### auth_service.py
- **목적**: 인증 비즈니스 로직 중앙. 로그인/회원가입/토큰 갱신 처리.
- **주요 함수**:
  - `authenticate(email, password)` → `User | None` — 자격 증명 검증
  - `create_tokens(user)` → `TokenPair` — access+refresh 발급
  - `refresh_access(refresh_token)` → `TokenPair` — 토큰 갱신
- **의존성**:
  - Import: `src/be/auth/models.py` (User 모델), `src/be/core/config.py` (JWT 설정)
  - Imported by: `src/be/auth/router.py` (API 핸들러), `src/be/middleware/auth.py` (미들웨어)

### jwt_utils.py
- **목적**: JWT 토큰 생성·검증 유틸리티
- **주요 함수**:
  - `encode_token(payload, secret, exp)` → `str`
  - `decode_token(token, secret)` → `dict`
- **상수**:
  - `ACCESS_TOKEN_EXP = 900` — 15분 (config override 가능)
  - `REFRESH_TOKEN_EXP = 604800` — 7일

### models.py
- **목적**: User, Role, UserRole SQLAlchemy 모델
- **주요 클래스**:
  - `User`: id, email, hashed_password, status, created_at
  - `Role`: id, name (enum: ADMIN/USER/GUEST)
  - `UserRole`: user_id, role_id (M:N 연결)
- **의존성**:
  - Imported by: `auth_service.py`, `router.py`
```

### 3.4 FE용 INDEX.md 형식

BE와 달리 FE는 **화면 중심**으로 기술한다.

```markdown
# src/fe/auth/ — 인증 화면 도메인

## 디렉토리 목적
로그인·회원가입·비밀번호 재설정 화면과 인증 상태 관리.

## 화면 인덱스

### LoginPage.tsx
- **화면 역할**: 이메일/비밀번호 로그인 폼
- **구성 컴포넌트**:
  - `LoginForm` — 입력 필드 + 유효성 검사
  - `OAuthButtons` — 소셜 로그인 버튼 그룹
  - `ErrorMessage` — API 에러 표시
- **상태 흐름**:
  - STATE_IDLE → STATE_LOADING(API 호출) → STATE_LOADED(대시보드 리다이렉트) / STATE_ERROR(에러 메시지)
- **API 의존성**:
  - POST `/auth/login` → `{ access_token, refresh_token }`
  - POST `/auth/oauth/{provider}` → 동일 응답
- **사용하는 공용 컴포넌트**: `Button`(shadcn), `Input`(shadcn), `useAuth`(hooks/)

### useAuth.ts
- **훅 역할**: 인증 상태 관리 + 토큰 저장
- **제공 값**:
  - `user: User | null` — 현재 로그인 사용자
  - `login(email, password)` → `void` — 로그인 실행
  - `logout()` → `void` — 토큰 폐기 + 리다이렉트
  - `isAuthenticated: boolean`
- **의존성**:
  - API 호출: `apiClient.post('/auth/login', ...)`, `apiClient.get('/auth/me')`
  - 사용처: `LoginPage`, `AuthGuard`, `UserMenu`

### constants.ts
- **목적**: 인증 관련 상수
- **상수**:
  - `AUTH_TOKEN_KEY = 'auth_token'` — 저장소 키
  - `LOGIN_REDIRECT = '/dashboard'` — 로그인 후 이동 경로
  - `SESSION_TIMEOUT = 900000` — 15분 (ms)
```

**FE meta의 핵심 차이:**
- BE는 **데이터 흐름·비즈니스 로직** 기준
- FE는 **화면 구성·사용자 경험·상태 전이** 기준
- 공통: 의존성(Import 관계)은 양쪽 모두 기술

### 3.5 meta 갱신 워크플로우

```
1. Task Brief에 "meta 갱신 항목" 섹션 포함
   예) ## meta 갱신
       - 신규 파일: src/be/auth/auth_service.py (인증 서비스)
       - 수정 파일: src/be/auth/models.py (User 모델에 status 필드 추가)

2. Task Brief 완료 시 BE/FE가 구현 요약을 보고
   → NEO가 docs/meta/src/be/INDEX.md 또는 해당 도메인 INDEX.md 갱신

3. git hook(post-commit)으로 meta 일관성 체크
   → 파일 추가/삭제가 meta에 반영됐는지 자동 감지 (선택적)
```

### 3.6 2-0 섹션 재작성 방향

현행:
```bash
grep -r "{기능 키워드}" src/be/
```

대체:
```markdown
1. docs/meta/src/be/INDEX.md 읽기 → 전체 백엔드 구조 파악
2. 해당 도메인의 INDEX.md 읽기 → 파일 목록과 용도 확인
3. 유사 기능 발견 시 → 해당 파일 직접 열어서 확인
4. 없으면 → 새 파일 생성 + Task Brief 완료 시 meta 갱신 항목 포함
```

## 4. FE에 대한 특별 고려사항

CEO가 FE 기준을 요청했으므로, BE와 구별되는 FE meta의 특성을 정리한다:

1. **화면 단위 인덱싱**: FE는 `src/fe/` 아래가 페이지·컴포넌트 중심이므로, meta도 "어떤 화면이 어떤 파일들로 구성되는가"를 기준으로 구성.
2. **상태 전이 기술**: STATE_LOADING → STATE_ERROR 같은 화면 상태 흐름은 FE 고유의 관심사. meta에 명시적으로 포함.
3. **공용 컴포넌트 재사용 추적**: `Button`, `Modal` 등 shadcn/ui 또는 자체 공용 컴포넌트의 사용처를 meta에 기록하면, "이 컴포넌트를 어디서 이미 썼는가"를 grep 없이 확인 가능.
4. **API 계약 연결**: 각 컴포넌트/페이지가 호출하는 API 엔드포인트를 meta에 명시 → `docs/design/api/`와의 정합성을 meta 수준에서 확인.

## 6. 결론

CEO의 `docs/meta/src/` 제안은 **grep의 구조적 한계를 근본적으로 해결**하는 우아한 설계다. 특히:

- 키워드 의존성 제거 → **의미 기반 코드 탐색**으로 전환
- 언어·프레임워크 독립적 → **진정한 범용성** 확보  
- LLM 최적화 → **토큰 효율** 향상
- Neo 산출물과 일관된 배치 → **docs/ 정책과 통합**

제안된 워크플로우(NEO 주도 갱신 + Task Brief 연동)를 통해 **meta 최신성 문제**를 해소하고, BE/FE의 2-0 섹션을 grep에서 meta 인덱스 읽기로 전환하면 Neo V2의 "DRY"는 비로소 실현된다.
