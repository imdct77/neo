## 1. 현행 접근의 구조적 문제

### 1.1 grep — 구문 검색이지 의미 검색이 아니다

```
grep -r "{기능 키워드}" src/be/
```

이 방식의 근본 결함:

| 문제 | 설명 |
|------|------|
| **키워드 의존** | `grep "payment"`는 `billing.py`를 놓친다. `grep "price"`는 `fee_calculator.py`를 놓친다. 같은 기능을 다른 이름으로 구현했으면 검출 불가. |
| **맥락 무지** | 검색 결과는 텍스트 매칭일 뿐이다. 그 함수가 정말로 "내가 찾는 기능"인지 구별하려면 파일을 직접 읽어야 함 → grep이 오히려 일을 늘린다. |
| **LLM 비효율** | BE가 수백 줄의 grep 결과를 읽고 판단해야 한다. 구현보다 탐색에 더 많은 토큰을 쓴다. |
| **언어 종속** | `grep -r`은 Python/Node/Go에서 동작하지만, 함수 시그니처 패턴은 언어마다 다르다. `def`, `func`, `const`, `export function` — grep은 구문을 알지 못한다. |
| **컨테이너 제약** | `grep`이 Docker 컨테이너에서 항상 사용 가능하다는 보장이 없다. search_files 도구가 있지만 이 역시 텍스트 매칭일 뿐. |

### 1.2 find + xargs — 프레임워크 종속

```bash
find src/fe/ -name "*.tsx" | xargs grep -l "{키워드}"
```

- `*.tsx`는 React/TypeScript 전용. Vue는 `.vue`, Svelte는 `.svelte`, Angular는 `.ts` + `.html`. 범용성 위배.
- Shell pipe(`|`)는 컨테이너 환경에서 불안정할 수 있다.

### 1.3 `constants/`, `types/` 경로 — 범용성 위배

```bash
grep -r "{상수명 후보}" src/be/ constants/
grep -r "{상수명 후보}" src/fe/constants/ src/fe/types/
```

방금 합의한 **"`src/be/`, `src/fe/`까지만 Neo가 정하고 하위 구조는 프로젝트 자유"** 원칙과 정면 충돌. NestJS는 `constants/` 없이 모듈별로 상수를 분산하고, Go는 `types/` 대신 패키지 단위로 타입을 정의한다.

### 1.4 DRY 원칙 자체의 구현이 DRY하지 않다

BE와 FE가 **똑같은 구조의 탐색 로직을 각자 중복해서 들고 있다**. 둘 다 "비슷한 것 찾기 → 재사용 판단 → 상수 충돌 확인"이라는 동일한 패턴인데, BE는 BE식으로, FE는 FE식으로 중복 기술돼 있다. DRY의 아이러니다.

## 2. CEO 제안: `docs/meta/src/` 구현 명세 메타 파일

### 2.1 제안 평가

| 장점 | 설명 |
|------|------|
| **의미 기반 탐색** | grep은 "어디에 `price`라는 문자열이 있는가"를 찾지만, meta는 "가격 계산을 담당하는 모듈은 어디인가"를 알려준다. 근본적 해결. |
| **LLM 친화적** | 마크다운은 LLM이 읽고 이해하기에 최적. grep 결과 200줄보다 meta 인덱스 50줄이 더 적은 토큰으로 더 정확한 판단을 내린다. |
| **언어·프레임워크 독립** | `.md` 파일은 모든 언어에서 동일하게 동작. `*.tsx` 같은 확장자 의존성 제거. |
| **Neo 산출물과의 통합** | `docs/` 아래 배치되어 기존 docs 디렉토리 정책과 일관성 유지. |
| **점진적 구축** | 코드를 쓸 때마다 meta도 같이 쌓인다. "한 번에 만들기" 부담 없음. |

### 2.2 보완이 필요한 지점

1. **작성 주체가 모호하다** — 누가 meta를 쓰는가? BE/FE가 직접? NEO가 취합?
2. **동기화 보장** — 코드는 수정됐는데 meta는 갱신 안 되면 오히려 grep보다 못한 misinformation이 된다.
3. **중복 기술** — meta의 설명과 코드 내 docstring/주석이 중복될 위험.
4. **디렉토리 구조 강제** — meta 트리가 `src/`의 디렉토리 트리를 그대로 따라가면, 프로젝트 구조 변경 시 meta도 전면 재작성.

## 3. 개량 제안: NEO 주도 메타 인덱스 + Task Brief 연동

### 3.1 핵심 아이디어

**meta는 NEO(orchestrator)가 관리한다.** BE/FE는 구현 시 "구현 명세 요약"을 Task Brief 완료 보고에 포함하고, NEO가 이를 meta 인덱스에 통합한다.

```
Task Brief → BE/FE 구현 → 완료 보고(구현 요약 포함) → NEO가 meta 갱신
```

### 3.2 디렉토리 구조 — 3단계 점진적 공개

컨텍스트 낭비를 막기 위해 meta는 **2개 파일 계층**으로 분리한다:

```
docs/meta/
  README.md                 ← meta 체계 설명 (이 문서)
  src/
    INDEX.md                ← L1: 전체 코드베이스 개요. BE/FE 디렉토리별
                               한 줄 목적 + "더 보려면 DETAIL.md" 링크.
                               신규 작업 시작 시 항상 로드. (300~500 토큰)
    be/
      INDEX.md              ← L1: 백엔드 최상위 디렉토리 목차
      DETAIL.md             ← L2+L3: 모든 도메인의 상세 인덱스 통합.
                               필요 시에만 로드. (파일별 함수·설계 의도)
      {domain}/
        INDEX.md            ← L1: 도메인별 파일 목록 + 한 줄 목적
        DETAIL.md           ← L2+L3: 도메인 내 모든 파일의 함수·상수·
                               설계 의도까지 전체 상세. 수정 시에만 로드.
    fe/
      INDEX.md              ← L1: 프론트엔드 최상위 디렉토리 목차
      DETAIL.md             ← L2+L3: 모든 도메인의 상세 인덱스 통합
      {domain}/
        INDEX.md            ← L1: 도메인별 파일 목록 + 한 줄 목적
        DETAIL.md           ← L2+L3: 도메인 내 모든 컴포넌트·훅·리렌더
                               분석까지 전체 상세
```

### 3.2-1. 탐색 규칙 (INDEX.md → DETAIL.md 유입)

**규칙: INDEX.md는 탐색 힌트만 제공한다. 판단이 필요하면 DETAIL.md로 진입한다.**

```
Step 1. docs/meta/src/INDEX.md 읽기 (L1, 항상)
  → BE/FE 각 디렉토리의 존재 여부와 한 줄 목적 파악.
    예) "auth/ — 인증·권한 관리" / "payment/ — 결제·환불 처리"
  → 작업과 관련된 디렉토리 식별.

Step 2. 해당 도메인의 INDEX.md 읽기 (L1)
  → 파일명 + 한 줄 목적 목록.
    예) "auth_service.py — 로그인·회원가입·토큰 갱신"
        "jwt_utils.py — JWT 인코딩/디코딩 유틸리티"
        "models.py — User/Role/UserRole DB 모델"

Step 3. 힌트 기반 판단
  ┌─ "내가 찾는 기능과 유사한 파일이 있는가?"
  │   YES → DETAIL.md를 읽어 해당 파일의 함수 시그니처·설계 의도 확인
  │         → 재사용 가능하면 import, 불가능하면 신규 구현
  │   NO  → 신규 구현. Task Brief 완료 시 meta 갱신 항목에 포함
  └─ "기존 파일을 수정해야 하는가?"
      YES → DETAIL.md를 읽어 수정 대상 파일의 의존성·주의사항 확인
          → 수정 후 영향 받는 파일들도 INDEX.md에서 식별

Step 4. 탐색 종료
  → DETAIL.md는 판단 완료 후 언로드 (컨텍스트 절약).
  → INDEX.md는 현재 작업 도메인 것이면 유지, 아니면 언로드.
```

**핵심 원칙:**
- INDEX.md 없는 디렉토리는 "아직 코드가 없다"는 신호 — DETAIL.md도 없다.
- INDEX.md는 **가벼움**이 핵심. 300~500토큰을 넘기지 않는다.
- DETAIL.md는 **필요할 때만** 로드. 수정·재사용 판단 시에만 진입.
- 상세도는 **INDEX.md ＜ DETAIL.md** 로 단방향. 역방향 참조 없음.

### 3.2-2. 파일 형식

### 3.3 L1 INDEX.md 형식 (가벼움 — 항상 로드)

INDEX.md의 유일한 목적은 **"이 디렉토리에 무엇이 있는가"** 를 300~500토큰으로 보여주는 것이다. 설계 의도·함수 상세는 DETAIL.md로 위임한다.

```markdown
# src/be/auth/ — 인증 도메인

## 디렉토리 목적
사용자 인증·권한 관리. JWT 발급·검증, OAuth 연동, 세션 관리.

## 파일 목록

| 파일 | 한 줄 목적 |
|------|-----------|
| `auth_service.py` | 로그인·회원가입·토큰 갱신 비즈니스 로직 중앙 |
| `jwt_utils.py` | JWT 인코딩/디코딩 저수준 유틸리티 — BE 전체 공용 |
| `models.py` | User, Role, UserRole DB 모델 |
| `router.py` | `/auth/*` API 엔드포인트 정의 |
| `dependencies.py` | FastAPI Depends — `get_current_user()` 등 |

→ 상세: [DETAIL.md](./DETAIL.md)
→ 이 디렉토리의 공용 함수: `jwt_utils.py`의 `encode_token()`, `decode_token()` — BE 전체에서 import
→ 다른 디렉토리의 공용 요소 사용: `src/be/core/config.py` (JWT_SECRET), `src/be/core/database.py` (DB 세션)
```

**INDEX.md 작성 원칙:**
- 파일별 한 줄로 충분. "무엇을 하는가"만 기술.
- 공용 함수 목록을 명시적으로 나열 — 신규 작업자가 "이미 있나?"를 INDEX.md 단계에서 판단.
- 외부 의존성(이 디렉토리가 import하는 다른 디렉토리의 공용 요소)도 기재 — 수정 시 영향 파악용.
- 500토큰 제한. 넘으면 디렉토리를 분할하거나 파일 그룹만 나열.

### 3.4 L2+L3 DETAIL.md 형식 (상세 — 필요 시에만 로드)

DETAIL.md는 **"이 코드가 왜 이렇게 작성되었는가"** 를 담는다. 설계 의도·재사용 규칙·리렌더 전파·수정 시 주의사항까지 포함. 아래는 BE/FE 각각의 예시.

#### 3.4-1. BE DETAIL.md 형식

```markdown
# src/be/auth/ — 인증 도메인

## 디렉토리 목적
사용자 신원 확인과 접근 권한 제어를 담당. 이 디렉토리의 모든 코드는
"누가 이 요청을 보냈는가"와 "이 요청을 보낼 자격이 있는가"라는
두 질문에 답하기 위해 존재한다. JWT 발급·검증, OAuth 연동, 세션
관리, 역할 기반 접근 제어(RBAC)를 포함한다.

## 파일 인덱스

### auth_service.py
- **목적**: 인증 흐름의 비즈니스 로직을 한 곳에 모은다. API 핸들러가
  개별적으로 인증 로직을 구현하지 않도록 중앙화한 서비스 레이어.
- **왜 이 파일이 존재하는가**: `POST /auth/login`, `POST /auth/register`,
  `POST /auth/refresh` 세 엔드포인트가 모두 동일한 토큰 생성·검증 로직을
  필요로 한다. 각 핸들러에 흩어져 구현되면 JWT 시크릿 변경 시 3곳을
  동시에 수정해야 하는 취약점이 생긴다. 이 파일은 그 취약점을 제거한다.
- **주요 함수**:
  - `authenticate(email: str, password: str) → User | None`
    * 하는 일: 이메일과 평문 비밀번호를 받아 DB의 해시와 대조.
    * 왜 존재: 로그인 API와 OAuth 최초 연동 시 계정 연결 확인에서
      동일하게 호출된다. 함수 하나로 두 흐름의 인증 로직을 통일.
    * 주의: 실패 시 None 반환. 호출측에서 None 체크 필수.
    * 절대 직접 수정하지 말 것: 비밀번호 해시 알고리즘 변경은
      `hash_password()`를 먼저 수정한 후 이 함수의 대조 로직을 맞춘다.
  - `create_tokens(user: User) → TokenPair`
    * 하는 일: User 객체로부터 access_token(JWT, 15분)과
      refresh_token(JWT, 7일)을 함께 발급.
    * 왜 존재: access+refresh 쌍은 항상 같이 발급되어야 하며,
      둘 중 하나만 발급되는 불일치 상태를 방지하기 위해 단일 함수로 묶음.
    * 공용 함수 여부: BE 전체에서 유일한 토큰 생성 진입점.
      다른 도메인에서 토큰 발급이 필요하면 이 함수를 import할 것.
      별도 `create_token()` 함수를 만들지 말 것.
  - `refresh_access(refresh_token: str) → TokenPair`
    * 하는 일: 유효한 refresh_token을 받아 새 access_token을 발급.
      동시에 refresh_token도 갱신(refresh rotation).
    * 왜 refresh_token도 갱신하는가: refresh_token 탈취 시 재사용을
      막기 위해 한 번 사용된 refresh_token은 폐기하고 새로 발급.
    * 주의: 만료된 refresh_token에 대해선 `RefreshTokenExpired` 예외 발생.
      호출측에서 401로 변환해야 함.
- **의존성**:
  - Import: `src/be/auth/models.py` (User), `src/be/core/config.py` (JWT_SECRET, JWT_EXP),
    `src/be/auth/jwt_utils.py` (encode/decode)
  - Imported by: `src/be/auth/router.py` (3개 엔드포인트), `src/be/middleware/auth.py`
    (모든 인증 필요 요청의 토큰 검증 미들웨어)

### jwt_utils.py
- **목적**: JWT 토큰의 저수준 생성·검증을 담당하는 순수 유틸리티.
  비즈니스 로직을 포함하지 않는다.
- **왜 이 파일이 존재하는가**: JWT 인코딩/디코딩은 PyJOSE 라이브러리에
  직접 의존하는 저수준 작업이며, auth_service.py와 middleware/auth.py
  양쪽에서 필요하다. 만약 JWT 라이브러리를 교체해야 한다면 이 파일만
  수정하면 된다. auth_service.py를 건드리지 않아도 된다.
- **공용 함수 여부: BE 전체 공용**. 모든 도메인이 이 파일을 import한다.
  새 도메인에서 JWT 토큰을 다뤄야 한다면 자체 `jwt_utils.py`를 만들지
  말고 이 파일을 import할 것. 동일한 기능의 함수가 두 파일에 존재하는
  것은 금지.
- **주요 함수**:
  - `encode_token(payload: dict, secret: str, exp: int) → str`
    * 하는 일: payload를 받아 서명된 JWT 문자열을 반환.
    * exp 파라미터는 초 단위. 호출측에서 `ACCESS_TOKEN_EXP` 또는
      `REFRESH_TOKEN_EXP` 상수를 전달한다.
    * 주의: payload에 민감 정보(비밀번호, 전체 User 객체)를 넣지 말 것.
      JWT는 서명만 되어있고 암호화되지 않았다. 최소한의 식별자만 포함.
  - `decode_token(token: str, secret: str) → dict`
    * 하는 일: JWT 문자열을 검증하고 payload dict를 반환.
    * 실패 시: 만료 → `TokenExpiredError`, 위조 → `InvalidTokenError`.
      이 두 예외를 구분하여 호출측에서 적절히 처리해야 한다.
    * 재시도 금지: 검증 실패는 일시적 오류가 아니다. retry 로직을
      넣지 말 것.
- **상수**:
  - `ACCESS_TOKEN_EXP = 900` (15분)
    * 왜 15분인가: access_token은 탈취되어도 15분 후 자동 만료되므로
      피해 범위가 제한된다. 5분은 너무 잦은 갱신으로 UX 저하,
      1시간은 탈취 시 노출 윈도우가 너무 길다.
    * 수정 시 영향: middleware/auth.py의 만료 처리 로직도 함께 검토.
  - `REFRESH_TOKEN_EXP = 604800` (7일)
    * 왜 7일인가: 사용자가 매일 재로그인하지 않아도 되는 UX와
      탈취된 refresh_token의 피해 윈도우 사이의 균형.
    * 수정 시: Redis에 저장된 refresh_token 블랙리스트 TTL도 일치시킬 것.

### models.py
- **목적**: 인증 도메인의 데이터 구조 정의. User, Role, UserRole
  세 모델로 사용자-역할 간 M:N 관계를 표현한다.
- **왜 Role이 별도 테이블인가**: "관리자", "일반 사용자", "게스트" 같은
  역할은 문자열 enum으로 하드코딩할 수도 있지만, 역할이 추가될 때마다
  migration 없이 DB 레벨에서 확장 가능하도록 정규화했다.
  Phase 2에서 커스텀 역할(프로젝트별 권한) 도입을 고려한 설계.
- **주요 클래스**:
  - `User`
    * 필드: id(UUID, PK), email(unique), hashed_password, status(enum:
      ACTIVE/INACTIVE/BANNED), created_at
    * status가 enum인 이유: 단순 boolean is_active로는 "비활성화(본인
      탈퇴)"와 "차단(관리자 제재)"을 구분할 수 없다. 두 경우 복구
      절차가 다르기 때문에 상태 머신으로 모델링.
    * 주의: email을 PK로 쓰지 않은 이유 — 사용자가 이메일 변경 시
      모든 FK가 깨지는 것을 방지. UUID를 불변 식별자로 사용.
  - `Role`
    * 필드: id(int, PK), name(enum: ADMIN/USER/GUEST)
    * 왜 int PK인가: 자주 JOIN되는 테이블이므로 UUID보다 int가
      인덱스 효율이 좋다. 역할은 수십 개 이하로 적기 때문.
  - `UserRole`
    * M:N 연결 테이블. user_id(UUID, FK→User) + role_id(int, FK→Role)
    * 복합 PK: (user_id, role_id) — 같은 user-role 쌍 중복 방지.
- **의존성**:
  - Imported by: `auth_service.py`, `router.py`, `middleware/auth.py`,
    `admin_service.py` (Phase 2)

## 화면 인덱스

### LoginPage.tsx
- **화면 역할**: `/login` 라우트. 이메일·비밀번호 로그인 + OAuth 로그인.
- **전용/공용**: 전용 페이지 컴포넌트. 이 페이지는 로그인 경로에서만
  사용된다. 다른 화면에서 재사용하지 않는다.
- **구성 컴포넌트 (복합 구조)**:
  - `LoginForm` — 이메일/비밀번호 입력 + 유효성 검사 + 제출
  - `OAuthButtons` — Google/GitHub/Kakao 소셜 로그인 버튼 그룹
  - `ErrorMessage` — API 4xx/5xx 에러 표시
- **리렌더 전파 분석**:
  * LoginPage 자체는 `useAuth()` 훅의 `login()` 함수를 호출할 뿐,
    내부 상태를 갖지 않는다. 따라서 LoginPage의 리렌더는 오직
    라우트 진입 시에만 발생.
  * `LoginForm` — 내부에서 `useState`로 email/password 상태를 관리.
    사용자가 입력할 때마다 LoginForm만 리렌더. OAuthButtons와
    ErrorMessage에는 전파되지 않음 (자식은 props 변경 시에만 리렌더).
  * `ErrorMessage` — 부모로부터 `error: string | null` prop을 받음.
    error가 null에서 문자열로 바뀔 때만 리렌더. 정상 입력 중에는
    리렌더 0회.
  * 주의: 만약 LoginPage에서 `useState`로 error를 관리하고
    email/password 입력 시에도 setState가 호출되면 LoginPage 전체가
    리렌더되어 OAuthButtons까지 불필요하게 다시 그려진다.
    현재 구조는 이 함정을 피하고 있다.
- **상태 흐름**:
  - STATE_IDLE: 초기 로딩 (빈 폼)
  - STATE_LOADING: API 호출 중 (버튼 비활성화 + 스피너)
  - STATE_ERROR: API 에러 (ErrorMessage 표시, 폼은 입력 유지)
    → 성공 시 대시보드로 리다이렉트하므로 STATE_LOADED는 불필요
- **API 의존성**:
  - POST `/auth/login` → `{ access_token, refresh_token }`
  - POST `/auth/oauth/{provider}` → 동일 응답 (OAuthButtons에서 호출)
- **사용하는 공용 요소**:
  - `Button` (shadcn/ui — 공용) — 제출 버튼. variant="default",
    disabled={isLoading}
  - `Input` (shadcn/ui — 공용) — 이메일·비밀번호 입력 필드
  - `useAuth()` (hooks/useAuth.ts — 공용 훅) — `login()` 함수 제공

### useAuth.ts
- **역할**: 인증 상태를 전역에서 관리하는 훅. Context API로 감싸져
  모든 컴포넌트에서 `useAuth()`로 접근 가능.
- **공용 여부**: **FE 전체 공용 훅.** 모든 도메인의 모든 컴포넌트가
  현재 로그인 사용자 정보를 얻거나 로그인·로그아웃을 실행할 때
  이 훅을 사용한다. 자체 `useUser()` 또는 `useSession()`을 만들지 말 것.
- **왜 전역 Context인가**: 사용자 정보(user)와 인증 여부(isAuthenticated)는
  헤더 네비게이션(사용자명 표시), 인증 가드(비로그인 리다이렉트),
  API 클라이언트(토큰 첨부) 등 10곳 이상에서 필요하다.
  각 컴포넌트가 개별로 API를 호출하면:
  (1) 중복 호출로 서버 부하 증가
  (2) 컴포넌트 간 user 정보 불일치 가능
  (3) 로그아웃 시 모든 컴포넌트가 개별 감지 불가
  → Context로 중앙화하여 세 가지 문제를 모두 제거.
- **제공 값과 설계 의도**:
  - `user: User | null`
    * null: 로그인 전 또는 토큰 만료. 모든 컴포넌트는
      user가 null인 경우를 반드시 처리해야 한다.
    * User 객체: API `/auth/me` 응답을 그대로 저장. 필요한 필드만
      선택적으로 꺼내 쓰지 않고 전체 객체를 보존하는 이유는,
      새 필드가 추가되어도 useAuth와 모든 소비자의 코드 수정이
      불필요하기 때문.
  - `login(email, password) → Promise<void>`
    * 성공 시: 내부에서 `apiClient.post('/auth/login')` 호출 →
      access_token을 메모리에 저장 → `setUser(response.user)` →
      `isAuthenticated = true`로 상태 갱신.
    * 실패 시: Error throw. 호출측에서 try/catch로 처리.
      useAuth 자체는 UI 에러 표시를 하지 않는다 (관심사 분리).
    * 주의: 이 함수는 비동기이므로 호출 중에는 `isAuthenticated`가
      여전히 false다. 버튼 비활성화 등 로딩 상태는 호출측에서 관리.
  - `logout() → void`
    * 하는 일: 메모리에서 access_token 삭제 → user = null →
      isAuthenticated = false → `/login`으로 리다이렉트.
    * 왜 API 호출이 없는가: JWT는 stateless다. 서버에 "로그아웃"을
      알릴 필요가 없다. 클라이언트에서 토큰을 폐기하는 것으로 충분.
      refresh_token 폐기는 필요하면 별도 호출.
  - `isAuthenticated: boolean`
    * `!!user`의 축약. user가 null이 아니면 true.
    * 주의: `isAuthenticated === true`라도 access_token이 만료되었을
      수 있다. API 401 응답은 apiClient의 interceptor가 처리하며,
      자동으로 refresh 시도 후 실패 시 logout()을 호출한다.
- **의존성**:
  - API 호출: `apiClient.post('/auth/login')`, `apiClient.get('/auth/me')`
  - 사용처: `LoginPage`, `AuthGuard(공용)`, `UserMenu(공용)`,
    `Header(공용)`, `apiClient.ts의 interceptor`

### OAuthButtons.tsx
- **역할**: 소셜 로그인 제공자(Google, GitHub, Kakao)의 로그인 버튼을
  하나의 그룹으로 묶어 렌더링.
- **공용 여부: 로그인 화면 전용.** 회원가입 화면(`RegisterPage`)에서도
  동일한 OAuth 버튼이 필요하므로 RegisterPage에서도 import하여 사용.
  하지만 대시보드, 설정 화면 등 인증 후 화면에서는 사용되지 않는다.
  → 준공용(semi-shared): auth 도메인 내에서만 공유. 다른 도메인에서는
  import 금지.
- **왜 컴포넌트로 분리했는가**: LoginPage와 RegisterPage가 완전히
  동일한 OAuth 로직과 UI를 필요로 한다. 각 페이지에 인라인으로
  버튼을 작성하면:
  (1) OAuth 제공자 추가 시 두 페이지 모두 수정 필요 (DRY 위반)
  (2) 버튼 스타일 불일치 가능성
  → 하나의 컴포넌트로 분리하여 두 곳에서 import.
- **리렌더 전파 분석**:
  * OAuthButtons는 props를 받지 않는다. 모든 상태는 내부에서
    `useAuth().login()` 호출로 처리.
  * LoginPage가 리렌더되어도 OAuthButtons는 props 변경이 없으므로
    리렌더되지 않는다 (React.memo 적용).
  * 주의: 만약 `React.memo` 없이 구현되었다면, LoginPage의
    email/password 입력 시마다 OAuthButtons가 불필요하게 리렌더됨.
    이 버튼들은 Google/GitHub 아이콘 SVG를 포함하므로 리렌더 비용이
    크다. 반드시 React.memo로 감쌀 것.
- **API 의존성**:
  - POST `/auth/oauth/google` → OAuth URL 반환 → 해당 URL로 리다이렉트
  - POST `/auth/oauth/github` → 동일 패턴
  - POST `/auth/oauth/kakao` → 동일 패턴
- **사용하는 공용 요소**:
  - `Button` (shadcn/ui — 공용) — variant="outline"

### AuthGuard.tsx
- **역할**: 인증되지 않은 사용자의 접근을 차단하는 래퍼 컴포넌트.
  children을 감싸고, isAuthenticated === false면 /login으로 리다이렉트.
- **공용 여부: FE 전체 공용.** 인증이 필요한 모든 라우트에서 사용.
- **왜 HOC나 미들웨어 대신 컴포넌트인가**: Next.js App Router의
  layout.tsx에서 직관적으로 감쌀 수 있어 라우트별 인증 정책을
  선언적으로 표현 가능.
- **리렌더 전파 분석**:
  * AuthGuard는 useAuth()의 isAuthenticated만 구독. user 객체의
    내부 필드 변경에는 반응하지 않는다.
  * isAuthenticated는 로그인/로그아웃 시에만 변경되므로,
    AuthGuard의 리렌더는 세션당 1~2회에 불과.
  * children은 isAuthenticated 변경 시에만 마운트/언마운트.
    정상 사용 중 불필요한 리렌더 0회.
- **의존성**:
  - Hook: `useAuth()` (공용)
  - 사용처: `app/(protected)/layout.tsx` — 모든 인증 필요 라우트

### constants.ts
- **목적**: 인증 도메인에서 사용되는 상수 정의.
- **공용 여부**: BE의 상수 파일이 아닌, FE auth 도메인 전용 상수.
  인증과 무관한 도메인에서 이 파일의 상수를 import하지 말 것.
- **상수와 설계 의도**:
  - `AUTH_TOKEN_KEY = 'auth_token'`
    * 어디에 쓰이나: apiClient의 interceptor에서 localStorage/memory
      키로 사용. access_token 저장·조회 시 이 키로 접근.
    * 왜 'token'이나 'jwt'가 아닌가: localStorage는 단일 도메인에서
      모든 앱이 공유한다. 다른 라이브러리와 키 충돌을 막기 위해
      네임스페이스를 포함. 'auth_' 접두사가 충돌 방지 역할.
    * 주의: localStorage 키를 변경하면 모든 기존 로그인 세션이
      무효화된다. 마이그레이션 코드 없이 이 값을 변경하지 말 것.
  - `LOGIN_REDIRECT = '/dashboard'`
    * 어디에 쓰이나: 로그인 성공 후 리다이렉트 목적지.
      LoginPage, OAuthButtons, AuthGuard 3곳에서 사용.
    * 왜 상수인가: 리다이렉트 경로가 3곳에 하드코딩되면 변경 시
      누락 위험. 하나의 상수로 중앙 관리.
    * 수정 시 영향: 이 값만 변경하면 된다. 컴포넌트 수정 불필요.
  - `SESSION_TIMEOUT = 900000` (15분, 밀리초)
    * 어디에 쓰이나: apiClient의 interceptor에서 access_token
      만료 1분 전에 자동 refresh를 트리거하는 타이머 기준.
    * 왜 BE의 `ACCESS_TOKEN_EXP`(15분)보다 짧은가: BE의 15분은
      토큰 자체의 수명, FE의 시간은 refresh 타이머. 1분의
      버퍼를 두어 네트워크 지연 중 토큰 만료를 방지.
    * 주의: 이 값을 BE의 ACCESS_TOKEN_EXP보다 크게 설정하면
      만료된 토큰으로 API를 호출하게 된다. 반드시 BE보다 작게.
```

**FE meta의 핵심 차이:**
- BE는 **데이터 흐름·비즈니스 로직의 "왜"** 에 초점
- FE는 **화면 구성 의도 + 리렌더 전파 추적 + 공용/전용 구분** 에 초점

### 3.6 meta 갱신 워크플로우

```
1. Task Brief에 "meta 갱신 항목" 섹션 포함
   예) ## meta 갱신
       - 신규 파일: src/be/auth/auth_service.py (인증 서비스)
       - 수정 파일: src/be/auth/models.py (User 모델에 status 필드 추가)

2. Task Brief 완료 시 BE/FE가 구현 요약을 보고
   → NEO가 docs/meta/src/INDEX.md + 해당 도메인 INDEX.md 갱신
   → 신규 파일이면 DETAIL.md에 템플릿 기반 항목 추가

3. git hook(post-commit)으로 meta 일관성 체크
   → 파일 추가/삭제가 meta에 반영됐는지 자동 감지 (선택적)
```

대체:
```markdown

```

## 4. FE에 대한 특별 고려사항

CEO가 FE 기준을 요청했으므로, BE와 구별되는 FE meta의 특성을 정리한다:

1. **화면 단위 인덱싱**: FE는 `src/fe/` 아래가 페이지·컴포넌트 중심이므로, meta도 "어떤 화면이 어떤 파일들로 구성되는가"를 기준으로 구성.
2. **상태 전이 기술**: STATE_LOADING → STATE_ERROR 같은 화면 상태 흐름은 FE 고유의 관심사. meta에 명시적으로 포함.
3. **공용 컴포넌트 재사용 추적**: `Button`, `Modal` 등 shadcn/ui 또는 자체 공용 컴포넌트의 사용처를 meta에 기록하면, "이 컴포넌트를 어디서 이미 썼는가"를 grep 없이 확인 가능.
4. **API 계약 연결**: 각 컴포넌트/페이지가 호출하는 API 엔드포인트를 meta에 명시 → `docs/design/api/`와의 정합성을 meta 수준에서 확인.

## 6. 결론

CEO의 `docs/meta/src/` 제안은 **grep의 구조적 한계를 근본적으로 해결**하는 우아한 설계다. 특히:

- 키워드 의존성 제거 → **의미 기반 코드 탐색**으로 전환
- 언어·프레임워크 독립적 → **진정한 범용성** 확보  
- LLM 최적화 → **토큰 효율** 향상
- Neo 산출물과 일관된 배치 → **docs/ 정책과 통합**

제안된 워크플로우(NEO 주도 갱신 + Task Brief 연동)를 통해 **meta 최신성 문제**를 해소하고, BE/FE의 2-0 섹션을 grep에서 meta 인덱스 읽기로 전환하면 Neo V2의 "DRY"는 비로소 실현된다.
