## 1. 현행 접근의 구조적 문제

### 1.1 grep — 구문 검색이지 의미 검색이 아니다

```
grep -r "{기능 키워드}" src/be/
```

이 방식의 근본 결함:

| 문제 | 설명 |
|------|------|
| **키워드 의존** | `grep "payment"`는 `billing.py`를 놓친다. `grep "price"`는 `fee_calculator.py`를 놓친다. 같은 기능을 다른 이름으로 구현했으면 검출 불가. |
| **맥락 무지** | 검색 결과는 텍스트 매칭일 뿐이다. 그 함수가 정말로 "내가 찾는 기능"인지 구별하려면 파일을 직접 읽어야 함 → grep이 오히려 일을 늘린다. |
| **LLM 비효율** | BE가 수백 줄의 grep 결과를 읽고 판단해야 한다. 구현보다 탐색에 더 많은 토큰을 쓴다. |
| **언어 종속** | `grep -r`은 Python/Node/Go에서 동작하지만, 함수 시그니처 패턴은 언어마다 다르다. `def`, `func`, `const`, `export function` — grep은 구문을 알지 못한다. |
| **컨테이너 제약** | `grep`이 Docker 컨테이너에서 항상 사용 가능하다는 보장이 없다. search_files 도구가 있지만 이 역시 텍스트 매칭일 뿐. |

### 1.2 find + xargs — 프레임워크 종속

```bash
find src/fe/ -name "*.tsx" | xargs grep -l "{키워드}"
```

- `*.tsx`는 React/TypeScript 전용. Vue는 `.vue`, Svelte는 `.svelte`, Angular는 `.ts` + `.html`. 범용성 위배.
- Shell pipe(`|`)는 컨테이너 환경에서 불안정할 수 있다.

### 1.3 `constants/`, `types/` 경로 — 범용성 위배

```bash
grep -r "{상수명 후보}" src/be/ constants/
grep -r "{상수명 후보}" src/fe/constants/ src/fe/types/
```

방금 합의한 **"`src/be/`, `src/fe/`까지만 Neo가 정하고 하위 구조는 프로젝트 자유"** 원칙과 정면 충돌. NestJS는 `constants/` 없이 모듈별로 상수를 분산하고, Go는 `types/` 대신 패키지 단위로 타입을 정의한다.

### 1.4 DRY 원칙 자체의 구현이 DRY하지 않다

BE와 FE가 **똑같은 구조의 탐색 로직을 각자 중복해서 들고 있다**. 둘 다 "비슷한 것 찾기 → 재사용 판단 → 상수 충돌 확인"이라는 동일한 패턴인데, BE는 BE식으로, FE는 FE식으로 중복 기술돼 있다. DRY의 아이러니다.

## 2. CEO 제안: `docs/meta/src/` 구현 명세 메타 파일

### 2.1 제안 평가

| 장점 | 설명 |
|------|------|
| **의미 기반 탐색** | grep은 "어디에 `price`라는 문자열이 있는가"를 찾지만, meta는 "가격 계산을 담당하는 모듈은 어디인가"를 알려준다. 근본적 해결. |
| **LLM 친화적** | 마크다운은 LLM이 읽고 이해하기에 최적. grep 결과 200줄보다 meta 인덱스 50줄이 더 적은 토큰으로 더 정확한 판단을 내린다. |
| **언어·프레임워크 독립** | `.md` 파일은 모든 언어에서 동일하게 동작. `*.tsx` 같은 확장자 의존성 제거. |
| **Neo 산출물과의 통합** | `docs/` 아래 배치되어 기존 docs 디렉토리 정책과 일관성 유지. |
| **점진적 구축** | 코드를 쓸 때마다 meta도 같이 쌓인다. "한 번에 만들기" 부담 없음. |

### 2.2 보완이 필요한 지점

1. **작성 주체가 모호하다** — 누가 meta를 쓰는가? BE/FE가 직접? NEO가 취합?
2. **동기화 보장** — 코드는 수정됐는데 meta는 갱신 안 되면 오히려 grep보다 못한 misinformation이 된다.
3. **중복 기술** — meta의 설명과 코드 내 docstring/주석이 중복될 위험.
4. **디렉토리 구조 강제** — meta 트리가 `src/`의 디렉토리 트리를 그대로 따라가면, 프로젝트 구조 변경 시 meta도 전면 재작성.

## 3. 개량 제안: NEO 주도 메타 인덱스 + Task Brief 연동

### 3.1 핵심 아이디어

**meta는 NEO(orchestrator)가 관리한다.** BE/FE는 구현 시 "구현 명세 요약"을 Task Brief 완료 보고에 포함하고, NEO가 이를 meta 인덱스에 통합한다.

```
Task Brief → BE/FE 구현 → 완료 보고(구현 요약 포함) → NEO가 meta 갱신
```

### 3.2 디렉토리 구조 — 소스 트리 미러링 (3계층)

meta 디렉토리 트리는 `src/` 아래의 **모든 디렉토리 구조를 그대로 따라간다.**
디렉토리 단위로 생성되며, 깊이 제한 없이 중첩된다.

```
소스 트리                          meta 트리 (3계층)
─────────                          ─────────────────
src/be/auth/                       docs/meta/src/be/auth/
                                     INDEX.md          ← L1: 파일·하위디렉토리 목록
                                     DETAIL.md         ← L2: 디렉토리 개요 + 파일별 목적·설계이유
                                     DETAIL.auth_service.md  ← L3: auth_service.py 상세
                                     DETAIL.jwt_utils.md     ← L3: jwt_utils.py 상세
src/be/auth/oauth/                 docs/meta/src/be/auth/oauth/
                                     INDEX.md          ← L1
                                     DETAIL.md         ← L2
                                     DETAIL.providers.md    ← L3
```

**3계층 구조:**

| 계층 | 파일 | 언제 로드 | 내용 | 토큰 |
|------|------|----------|------|:---:|
| **L1** | `INDEX.md` | 항상 (신규 작업 시작 시) | [파일] 목록 (한 줄) + [하위 디렉토리] 목록 + 공용 요소 | ~400 |
| **L2** | `DETAIL.md` | "자세히 봐야겠다" 판단 시 | 디렉토리 목적 + 하위 디렉토리 설명 + 파일별 목적·설계 이유·공용 여부 | ~1500 |
| **L3** | `DETAIL.{filename}.md` | 특정 파일을 수정·재사용할 때만 | 함수 시그니처·구현 상세·의존성·수정 주의사항·리렌더 분석 | 파일당 ~500 |

**규칙:**
- 코드가 있는 모든 디렉토리는 **반드시 INDEX.md를 갖는다.**
- 공용 요소가 있거나 설계 의도 설명이 필요하면 DETAIL.md를 생성.
- 파일 수정·재사용 판단이 필요할 정도로 복잡한 파일은 L3 DETAIL.{파일명}.md를 생성.
- 빈 디렉토리는 어떤 meta 파일도 갖지 않는다.

### 3.2-1. 탐색 규칙 (L1 → L2 → L3 단계적 진입)

**핵심: INDEX.md는 "여기 무엇이 있나"만 보여준다. 판단이 필요할 때만 더 깊게 들어간다.**

```
Step 1. docs/meta/src/INDEX.md 읽기 (L1, 항상)
  → be/와 fe/ 선택.

Step 2. be/INDEX.md 읽기 (L1)
  → 바로 아래 디렉토리 목록.
    예) auth/ — 인증·권한. 공용: jwt_utils, AuthGuard

Step 3. auth/INDEX.md 읽기 (L1)
  → [파일] 섹션 + [하위 디렉토리] 섹션.
    [파일]
      auth_service.py   — 로그인·회원가입·토큰 갱신
      jwt_utils.py      — JWT 인코딩/디코딩 (BE 전체 공용)
    [하위 디렉토리]
      oauth/            — OAuth 제공자별 연동 → oauth/INDEX.md

Step 4. 판단 — 어느 계층까지 들어갈 것인가
  ┌─ "파일 목록만 봐도 충분. 신규 구현이다" → 탐색 종료. 구현 시작.
  ├─ "이 디렉토리가 정확히 무엇을 하는지 더 알아야겠다"
  │   → DETAIL.md (L2) 로드
  │   → 디렉토리 목적 + 파일별 설계 의도 읽고 판단
  └─ "특정 파일을 수정하거나 재사용해야 한다"
      → DETAIL.{파일명}.md (L3) 로드
      → 함수 시그니처·의존성·수정 주의사항 확인 후 작업

Step 5. 탐색 종료
  → 판단 완료된 L2/L3 파일은 언로드 (컨텍스트 절약).
  → INDEX.md는 현재 작업 디렉토리 것만 유지.
```

**탐색 비용:** L1만으로 80% 케이스 판단 가능. L2는 15%, L3는 5%.
grep으로 매번 수백 줄 읽던 것과 비교하면 토큰 소비가 1/10 이하.

### 3.3 L1 INDEX.md 형식

INDEX.md의 유일한 목적은 **"이 디렉토리에 무엇이 있는가"** 를 300~500토큰으로 보여주는 것이다.
파일 목록과 하위 디렉토리 목록을 구분하여 네비게이션 힌트를 제공한다.

```markdown
# src/be/auth/ — 인증 디렉토리

## 디렉토리 목적
사용자 인증·권한 관리. JWT 발급·검증, OAuth 연동, 세션 관리.

## 파일 목록

| 파일 | 한 줄 목적 |
|------|-----------|
| `auth_service.py` | 로그인·회원가입·토큰 갱신 비즈니스 로직 중앙 |
| `jwt_utils.py` | JWT 인코딩/디코딩 저수준 유틸리티 — BE 전체 공용 |
| `models.py` | User, Role, UserRole DB 모델 |
| `router.py` | `/auth/*` API 엔드포인트 정의 |
| `dependencies.py` | FastAPI Depends — `get_current_user()` 등 |

## 하위 디렉토리

| 디렉토리 | 한 줄 목적 | 링크 |
|---------|-----------|------|
| `oauth/` | Google·GitHub·Kakao OAuth 제공자별 연동 | → `oauth/INDEX.md` |
| `middleware/` | JWT 토큰 검증 미들웨어 | → `middleware/INDEX.md` |

→ 상세: [DETAIL.md](./DETAIL.md)
→ 공용 요소: `jwt_utils.py` — BE 전체에서 import
```

**INDEX.md 작성 원칙:**
- 파일별 한 줄. "하는 일"만 기술. "왜"는 L2로 위임.
- [하위 디렉토리] 섹션은 **필수.** 자식 디렉토리가 없으면 "없음"으로 명시.
- 공용 요소 목록을 명시 — 신규 작업자가 INDEX.md만 읽고 "이미 있나?" 판단 가능.
- 500토큰 제한.

### 3.4 L2 DETAIL.md 형식 — 디렉토리 개요 + 설계 의도

DETAIL.md는 **"이 디렉토리와 파일들이 왜 이렇게 구성되었는가"** 를 설명한다.
파일별로 목적과 설계 이유까지만 기술하고, 함수 시그니처·구현 상세는 L3로 위임한다.

#### 3.4-1. BE DETAIL.md 예시

```markdown
# src/be/auth/ — 인증 디렉토리 상세

## 디렉토리 목적
사용자 신원 확인과 접근 권한 제어를 담당. 이 디렉토리의 모든 코드는
"누가 이 요청을 보냈는가"와 "이 요청을 보낼 자격이 있는가"라는
두 질문에 답하기 위해 존재한다.

## 하위 디렉토리 인덱스

| 디렉토리 | 목적 |
|---------|------|
| `oauth/` | Google·GitHub·Kakao OAuth 2.0 제공자별 인증 흐름 구현. 제공자별 차이를 개별 파일로 격리하여 추가·제거가 용이하도록 설계. → `oauth/DETAIL.md` |
| `middleware/` | 모든 HTTP 요청의 JWT 토큰을 검증하는 FastAPI 미들웨어. 인증이 필요한 라우트에 일괄 적용. → `middleware/DETAIL.md` |

## 파일 인덱스

### auth_service.py
- **목적**: 인증 비즈니스 로직을 한 곳에 중앙화. 로그인·회원가입·토큰 갱신의 세 흐름이 동일한 토큰 생성·검증 로직을 공유한다.
- **왜 이 파일이 존재하는가**: `POST /auth/login`, `POST /auth/register`, `POST /auth/refresh` 세 엔드포인트가 흩어져 구현되면 JWT 시크릿 변경 시 3곳을 동시에 수정해야 하는 취약점이 생긴다. 이 파일은 그 취약점을 제거한다.
- **공용 여부**: 디렉토리 전용. 다른 도메인에서 직접 import하지 않는다.
- **주요 함수 개요**:
  - `authenticate()` — 이메일·비밀번호 검증 → User | None
  - `create_tokens()` — access+refresh 토큰 쌍 발급. **BE 전체에서 유일한 토큰 생성 진입점.**
  - `refresh_access()` — refresh_token으로 access_token 갱신 (rotation 적용)
- → 상세: [DETAIL.auth_service.md](./DETAIL.auth_service.md)

### jwt_utils.py
- **목적**: JWT 토큰의 저수준 생성·검증. PyJOSE 의존성을 이 파일 하나로 격리.
- **왜 이 파일이 존재하는가**: auth_service.py와 middleware/auth.py 양쪽에서 JWT 인코딩/디코딩이 필요하다. 라이브러리 교체 시 이 파일만 수정하면 된다.
- **공용 여부**: **BE 전체 공용.** 새 도메인에서 JWT 토큰을 다뤄야 한다면 이 파일을 import할 것. 자체 jwt_utils를 만들지 말 것.
- **주요 함수 개요**:
  - `encode_token()` — payload → 서명된 JWT 문자열
  - `decode_token()` — JWT 문자열 검증 → payload dict
- **상수 개요**:
  - `ACCESS_TOKEN_EXP=*** 탈취 피해 윈도우(15분)와 UX 사이의 균형
  - `REFRESH_TOKEN_EXP=*** 재로그인 빈도(7일)와 탈취 윈도우 사이의 균형
- → 상세: [DETAIL.jwt_utils.md](./DETAIL.jwt_utils.md)

### models.py
- **목적**: User, Role, UserRole DB 모델. 인증 도메인의 데이터 구조.
- **왜 이 파일이 존재하는가**: Role을 enum이 아닌 별도 테이블로 정규화하여 Phase 2의 커스텀 역할 확장을 대비.
- **공용 여부**: BE 전체에서 import (User 모델은 거의 모든 도메인이 참조).
- **주요 모델 개요**:
  - `User` — UUID PK, email(unique), hashed_password, status(ACTIVE/INACTIVE/BANNED)
  - `Role` — int PK, name(ADMIN/USER/GUEST)
  - `UserRole` — M:N 연결 (user_id, role_id 복합 PK)
- → 상세: [DETAIL.models.md](./DETAIL.models.md)
```

#### 3.4-2. FE DETAIL.md 예시

```markdown
# src/fe/auth/ — 인증 화면 디렉토리 상세

## 디렉토리 목적
로그인·회원가입·비밀번호 재설정·OAuth 연동 화면과 인증 상태 관리.
모든 컴포넌트는 "인증되지 않은 사용자"를 위한 UI이며, 인증 완료 후 타 도메인으로 리다이렉트된다.

## 하위 디렉토리 인덱스

| 디렉토리 | 목적 |
|---------|------|
| `components/` | 인증 폼에서 재사용되는 UI 컴포넌트 (OAuthButtons, ErrorMessage 등). auth 도메인 내 공용. → `components/DETAIL.md` |

## 파일 인덱스

### LoginPage.tsx
- **목적**: `/login` 라우트. 이메일·비밀번호 로그인 + OAuth 로그인 UI.
- **왜 이 컴포넌트가 존재하는가**: 로그인은 서비스 진입의 관문. 모든 인증 방식(이메일, OAuth)을 한 화면에서 제공하여 사용자가 선택지를 한눈에 볼 수 있도록 통합.
- **공용 여부**: 전용 페이지. 다른 화면에서 재사용하지 않는다.
- **구성 컴포넌트**: LoginForm, OAuthButtons, ErrorMessage
- **리렌더 전파**: LoginPage 자체는 상태가 없어 라우트 진입 시에만 렌더. LoginForm의 useState는 자신만 리렌더하며 OAuthButtons로 전파되지 않음.
- → 상세: [DETAIL.LoginPage.md](./DETAIL.LoginPage.md)

### useAuth.ts
- **목적**: 인증 상태(Context)를 전역에서 관리하는 훅.
- **왜 이 훅이 존재하는가**: user 정보는 Header, AuthGuard, apiClient 등 10곳 이상에서 필요. 각 컴포넌트가 개별 API 호출 시 서버 부하·정보 불일치·로그아웃 감지 실패가 발생. Context로 중앙화하여 해결.
- **공용 여부**: **FE 전체 공용.** 자체 useUser(), useSession()을 만들지 말 것.
- **제공 값 개요**: user, login(), logout(), isAuthenticated
- → 상세: [DETAIL.useAuth.md](./DETAIL.useAuth.md)

### AuthGuard.tsx
- **목적**: 인증 필요 라우트를 보호하는 래퍼. isAuthenticated가 false면 /login으로 리다이렉트.
- **왜 HOC 대신 컴포넌트인가**: layout.tsx에서 선언적으로 감싸 라우트별 인증 정책을 직관적으로 표현 가능.
- **공용 여부**: **FE 전체 공용.** 모든 인증 필요 라우트에서 사용.
- **리렌더 전파**: isAuthenticated만 구독. 세션당 1~2회 리렌더. children은 인증 상태 변경 시에만 마운트/언마운트.
- → 상세: [DETAIL.AuthGuard.md](./DETAIL.AuthGuard.md)
```

## 함수 상세

### authenticate(email: str, password: str) → User | None
- **하는 일**: 이메일과 평문 비밀번호를 받아 DB의 해시와 대조.
- **호출처**: POST `/auth/login`, OAuth 최초 연동 시 계정 연결 확인.
- **실패 시**: None 반환. 호출측에서 None 체크 후 401 응답.
- **수정 시 주의**: 비밀번호 해시 알고리즘 변경은 `hash_password()`를 먼저 수정한 후 이 함수의 대조 로직을 맞출 것.

### create_tokens(user: User) → TokenPair
- **하는 일**: User → access_token(JWT, 15분) + refresh_token(JWT, 7일) 발급.
- **호출처**: authenticate() 성공 후, refresh_access() 성공 후.
- **중복 금지**: BE 전체에서 유일한 토큰 생성 진입점. 다른 도메인에서 별도 create_token()을 만들지 말 것.
- **수정 시 영향**: access_token 만료 시간 변경 → JWT_EXP 상수 + FE의 SESSION_TIMEOUT도 함께 검토.

### refresh_access(refresh_token: str) → TokenPair
- **하는 일**: 유효한 refresh_token → 새 access+refresh 쌍 발급 (rotation).
- **실패 시**: 만료 → `RefreshTokenExpired`, 위조 → `InvalidTokenError`. 호출측에서 401로 변환.
- **수정 시 주의**: refresh_token 폐기 로직 변경 시 Redis 블랙리스트 TTL도 일치시킬 것.

## 의존성

- `src/be/auth/models.py` → `User` — 사용자 모델
- `src/be/auth/jwt_utils.py` → `encode_token()`, `decode_token()`

## 4. FE에 대한 특별 고려사항

CEO가 FE 기준을 요청했으므로, BE와 구별되는 FE meta의 특성을 정리한다:

1. **화면 단위 인덱싱**: FE는 `src/fe/` 아래가 페이지·컴포넌트 중심이므로, meta도 "어떤 화면이 어떤 파일들로 구성되는가"를 기준으로 구성.
2. **상태 전이 기술**: STATE_LOADING → STATE_ERROR 같은 화면 상태 흐름은 FE 고유의 관심사. meta에 명시적으로 포함.
3. **공용 컴포넌트 재사용 추적**: `Button`, `Modal` 등 shadcn/ui 또는 자체 공용 컴포넌트의 사용처를 meta에 기록하면, "이 컴포넌트를 어디서 이미 썼는가"를 grep 없이 확인 가능.
4. **API 계약 연결**: 각 컴포넌트/페이지가 호출하는 API 엔드포인트를 meta에 명시 → `docs/design/api/`와의 정합성을 meta 수준에서 확인.

## 6. 결론

CEO의 `docs/meta/src/` 제안은 **grep의 구조적 한계를 근본적으로 해결**하는 우아한 설계다. 특히:

- 키워드 의존성 제거 → **의미 기반 코드 탐색**으로 전환
- 언어·프레임워크 독립적 → **진정한 범용성** 확보  
- LLM 최적화 → **토큰 효율** 향상
- Neo 산출물과 일관된 배치 → **docs/ 정책과 통합**

제안된 워크플로우(NEO 주도 갱신 + Task Brief 연동)를 통해 **meta 최신성 문제**를 해소하고, BE/FE의 2-0 섹션을 grep에서 meta 인덱스 읽기로 전환하면 Neo V2의 "DRY"는 비로소 실현된다.
